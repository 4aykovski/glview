# gitlab-tui — спецификация

Версия: 0.1 (черновик) · 2026-10-19 · дизайн экранов: [gitlab-tui screens](https://claude.ai/artifact/XeDkUTkXVZ2Dg6sFAnmai2)

gitlab-tui — терминальный клиент GitLab на Go + Bubble Tea для личного использования. Он открывает MR, пайплайны, логи джоб, теги и issues текущего проекта или целой папки с проектами и делает частые действия без браузера.

Дизайн-макеты (локальная копия — [docs/design/](design/README.md)) задают раскладку, разделители и рамки, колонки, тексты и хоткеи; при расхождении хоткеев приоритет у раздела 3.1. Hex-цвета и размеры шрифта в макетах иллюстративные: в реализации все цвета берутся из 16 ANSI-цветов терминала (раздел 9).

---

## 1. Цели и не-цели

### Цели

1. Открыть gitlab-tui в папке проекта и сразу увидеть его MR, пайплайны, issues и теги.
2. Открыть gitlab-tui в папке с проектами (workspace) и одним экраном увидеть MR, пайплайны и теги по всем проектам. Нагрузка на GitLab — один GraphQL-запрос на пачку проектов.
3. Делать частые действия без браузера: approve, merge, rebase, retry/cancel/play джобы, запуск пайплайна с переменными, создание и удаление тега, комментарий и close/reopen для issue. После MVP: просмотр диффа MR и комментарии к строкам (3.5, T35), To-Do list (3.17, T36), создание MR формой (3.18, T37).
4. Читать лог джобы в реальном времени: ANSI-цвета, сворачиваемые секции, поиск.
5. Работать с self-hosted GitLab: свой URL, relative URL root, нестандартный SSH-порт, свой CA.
6. Русский и английский интерфейс с переключением на лету.
7. Выглядеть как терминал пользователя: только ANSI-цвета, без своей палитры. Архитектура сразу готова к кастомным темам.
8. Обновлять локальные клоны одной кнопкой: fetch всех проектов workspace, pull только fast-forward.

### Не-цели (MVP)

- Несколько инстансов GitLab одновременно (один хост на запуск).
- Редактирование меток, assignee, milestone у существующих MR и issue; создание issue. MR создаётся формой (3.18), но не редактируется.
- Ответы в треды и resolve тредов; подсветка синтаксиса в диффах; дифф отдельного коммита и сравнение версий MR.
- Уведомления, кроме счётчика To-Do в шапке (3.0, 3.17).
- Встроенные палитры и пользовательские темы.
- Хоткеи на русской раскладке.
- Замена `git`: TUI не делает push, commit, локальный merge/rebase и не разрешает конфликты. Из локальных git-операций есть только fetch, pull fast-forward (раздел 10.4) и checkout МРа через `glab`.

## 2. Режимы запуска и навигация

### 2.1. Порядок старта

```
старт
 ├─ загрузить конфиг (~/.config/gitlab-tui/config.yaml, может отсутствовать)
 ├─ определить контекст:
 │    -p group/project            → режим проекта (по флагу)
 │    есть .git в cwd или выше     → режим проекта (по remote origin)
 │    иначе                        → режим workspace (скан подпапок на 1 уровень)
 ├─ определить хост:   config.host → env GITLAB_HOST → хост remote (режим проекта) → экран настройки
 ├─ найти токен:       config.token → env GITLAB_TOKEN → glab → экран настройки
 ├─ GET /user (проверка токена, имя для шапки; кэш на сессию)
 └─ открыть корневой экран режима
```

**Флаги CLI:**

| Флаг | Значение |
|---|---|
| `-p, --project <path\|url>` | открыть проект напрямую: `group/sub/project` или полный URL проекта |
| `--config <file>` | другой конфиг |
| `--debug` | писать лог в `$XDG_CACHE_HOME/gitlab-tui/debug.log`; токены в логе маскируются |
| `--version` | версия и выход |

### 2.2. Режим проекта

- Ищем `.git`, поднимаясь от cwd к корню, как git. Останавливаемся на первом найденном.
- `.git` — каталог: читаем `.git/config` и `.git/HEAD`.
- `.git` — файл со строкой `gitdir: <path>` (worktree или сабмодуль): путь относительный от файла.
  - Worktree: в gitdir есть файл `commondir`. `config` читаем из commondir, `HEAD` — из самого gitdir.
  - Сабмодуль: gitdir указывает на `.git/modules/<name>`, там свой `config` и `HEAD`.
- Remote: `[remote "origin"] url`. Если `origin` нет и remote ровно один, берём его. Иначе проект не определён.
- Ветка: `HEAD` = `ref: refs/heads/<branch>` → имя ветки; detached HEAD → короткий SHA.
- Для определения проекта `git` как процесс не вызываем: чтение файлов мгновенное и работает без git. `git` запускается только для fetch, pull и подсчёта ↑↓ (раздел 10.4).
- Открывается корневой экран проекта на табе MRs.

### 2.3. Режим workspace

- В cwd нет `.git` ни в нём, ни выше. Сканируем непосредственные подпапки (1 уровень), скрытые пропускаем, по симлинкам на каталоги переходим.
- Для каждой подпапки с `.git` разбираем remote так же, как в 2.2:
  - хост remote = хост инстанса (или его алиас) → GitLab-проект;
  - иначе → строка серым «не GitLab / другой инстанс»;
  - подпапки без `.git` не показываем, в футере таба «Проекты» — сводка «пропущено без .git: notes, tmp».
- Открывается корневой экран workspace на табе «Проекты».

### 2.4. Пограничные случаи старта

| Ситуация | Поведение |
|---|---|
| В workspace ни одного GitLab-проекта | Экран workspace с пустым состоянием: «В ~/src нет GitLab-проектов: просмотрено N папок, из них k с чужим remote, m без .git». Подсказки: `p` выбрать проект, `F` поиск по GitLab, `q` выход. Серые не-GitLab папки всё равно показываются. |
| Режим проекта, remote на другой хост (github.com, другой GitLab) | Экран «Проект не на gitlab.example.com»: remote, его хост, настроенный хост. Действия: `p`, `F`, `w` открыть workspace родительской папки, `q`. |
| Remote на хост инстанса, но проект не найден (404) | Тот же экран с текстом «проект не найден или нет доступа», 404 и 403 не различаем. |
| Хоста нет нигде (нет конфига, env и remote) | Экран первичной настройки. |
| Хост из remote, токена нет ни в env, ни в glab | Экран настройки с подставленным URL. |
| SSH-алиас (`git@gitlab-work:group/proj.git`) | Совпадает, если алиас перечислен в `host_aliases` конфига. `~/.ssh/config` не разбираем. |
| `insteadOf` в gitconfig | Не поддерживается, см. допущения. |
| Detached HEAD, пустой репозиторий без коммитов | Ветка показывается как короткий SHA или `—`, работа не блокируется. |

### 2.5. Разбор URL remote

Поддерживаемые формы:

- `git@host:group/sub/proj.git`
- `ssh://git@host[:port]/group/sub/proj.git`
- `https://host[:port][/prefix]/group/sub/proj[.git]`
- `http://…`

Путь проекта = путь URL без `.git`. Если в `host` конфига есть path-prefix (relative URL root, например `https://example.com/gitlab`), префикс отрезается. Хосты сравниваются без регистра и без порта: SSH-порт и HTTP-порт у self-hosted обычно разные.

### 2.6. Карта экранов

```
                    ┌────────────── Setup (первый запуск) ──────────────┐
                    ▼                                                   │
   ┌─────────── Workspace ───────────┐   f / enter на проекте   ┌──── Project ────┐
   │ 1 Проекты 2 MRs 3 Pipelines     │ ───────────────────────▶ │ 1 MRs 2 Pipelines│
   │ 4 Tags  (группы по проектам)    │ ◀─────── esc ─────────── │ 3 Issues 4 Tags  │
   └──────┬──────────────────────────┘                          └──┬───────────────┘
          │ enter на MR / пайплайне / теге                          │ enter
          ▼                                                         ▼
     MR detail ── enter на пайплайне ──▶ Pipeline ── enter на джобе ──▶ Job log
                                          │  enter на bridge
                                          └──▶ Pipeline (downstream, другой проект)
     Issue (enter в табе Issues)
     New MR (n в табе MRs) ── создан ──▶ MR detail (вместо формы)

   To-Do (T откуда угодно) ── enter ──▶ MR detail / Issue / браузер

Оверлеи поверх любого экрана: ? Help · p Project picker · F Global search ·
Confirm · Merge · Run pipeline · Play job · New tag · Comment
```

- **Стек экранов.** `enter` кладёт экран на стек (`PushMsg`), `esc` снимает (`PopMsg`). На корневом экране `esc` ничего не делает, `q` — выход. `ctrl+c` — выход откуда угодно.
- **Стартовый корень не заменяется поиском.** Экран, с которого начался запуск (Workspace папки или Project), остаётся на дне стека, пока не завершится gitlab-tui; `p`/`F` кладут экраны над ним, и `esc` возвращает к нему в прежнем состоянии (таб, курсор, свёрнутые группы, фильтры). Заменяют корень только setup и экраны старта (`ReplaceRoot`).
- **`enter` на проекте в `p`/`F`** закрывает всё выше верхнего Workspace стека и кладёт над ним Project. Если Workspace в стеке нет (старт в режиме проекта), закрывается всё выше корня, Project кладётся над корнем.
- **`enter` на группе в `F`** закрывает всё выше корня и кладёт над ним Workspace из проектов группы. Workspace группы в стеке не больше одного: новая группа заменяет прежнюю. `esc` на Workspace группы возвращает к стартовому корню.
- Пример: старт в `~/src` → `F` → группа `platform` → `p` → `platform/route-service`: стек `[Workspace ~/src, Workspace group: platform, Project]`; `esc`, `esc` — снова `~/src` с прежним курсором.
- **`T` — To-Do** (3.17). Если экран To-Do уже есть в стеке, закрывается всё выше него, и он становится вершиной (с обновлением). Иначе To-Do кладётся над текущей вершиной. `esc` на To-Do возвращает к экрану, с которого его открыли.

### 2.7. Решение: фильтр по проекту в workspace = режим проекта

Сливаем. В workspace `f` на строке любого таба (или `enter` на табе «Проекты») кладёт на стек экран Project для этого проекта. Открывается тот же таб: MRs → MRs, Pipelines → Pipelines, Tags → Tags. В шапке крошки `~/src › frontend/route-planner-ui`, `esc` возвращает в workspace, его состояние (таб, курсор, свёрнутые группы) не теряется: он лежит ниже по стеку.

Почему:

1. **Один код списков.** Списки MR, пайплайнов и тегов одного проекта реализуются один раз: `Scope` с одним проектом, страницы по 20 и подгрузка при скролле.
2. **Больше возможностей при фильтре.** В отфильтрованном виде сразу доступны полные фильтры (state, reviewer, labels, source…), таб Issues и все действия режима проекта. В «урезанном фильтре» workspace их бы не было.
3. **Навигация не меняется.** Стек уже есть: «назад в workspace» — это обычный `esc`.

Цена: в отфильтрованном виде нет таба «Проекты», а таб 1 означает MRs, а не «Проекты». Это приемлемо: шапка явно показывает режим.

Отличие от макета `WSMRsProject`: там фильтр — чип `проект: … ✕` внутри workspace. Вместо чипа будут крошки, по смыслу и раскладке то же самое.

## 3. Экраны

### 3.0. Общий каркас

Каркас экрана сверху вниз:

1. Шапка: `gitlab-tui  <проект | ~/путь · workspace · N GitLab-проектов>  · хост` слева, `@user · To-Do 5 · ⟳ <сколько назад обновлено> [(live: N running)]` справа. `To-Do N` — число невыполненных задач To-Do (3.17), Accent; при нуле или пока число не известно — не показывается; при нехватке ширины шапки выпадает первым.
2. Табы: `1 MRs 6  2 Pipelines  3 Issues 12  4 Tags` (число — счётчик, если известен).
3. Строка фильтров: `state:opened  scope:all  reviewer:@me  draft:any`, справа сортировка или `20 из 1 482`.
4. Контент: таблица с заголовком колонок.
5. Превью выбранной записи в рамке.
6. Футер: хоткеи слева (ужимаются по приоритету), справа последний тост или статус.

**Колонки таблиц** имеют приоритет. При узкой ширине сначала исчезают колонки с низким приоритетом, потом обрезаются (`…`) текстовые. Минимальный поддерживаемый размер терминала — 80×24. При ширине меньше 100 колонок превью скрывается и открывается по `enter`.

**Хоткеи и поля ввода.** Пока фокус в текстовом поле (фильтр `/`, формы), однобуквенные хоткеи отключены. `esc` выходит из поля.

**Разрешённые конфликты:**

- **`m`: merge vs фильтр «я».** `m` везде остаётся фильтром «я»: он глобальный и нужен в каждом табе. Merge — `M`, открывает диалог merge. В диалоге выбор «сейчас / когда пайплайн пройдёт» (auto-merge), чекбоксы squash и «удалить ветку». Отдельный хоткей для «merge when pipeline succeeds» не нужен: это вариант в том же диалоге, и в нём по умолчанию выбран auto-merge, если пайплайн ещё идёт.
- **`l`: лог vs `h/l` в пайплайне.** Внутри Pipeline `h/l` — навигация по стейджам-колонкам (как в макете), лог открывается `enter`. В списке пайплайнов `l` — короткий путь к логу первой упавшей или running джобы.
- **Checkout — `C`.** Не занят ни в одном контексте MR и совпадает с примером custom command из брифа. `c` в MR — комментарий, `C` — checkout.
- **`a` в Pipeline — попытки джобы.** В макете `a` — артефакты, но они убраны из MVP, а к прежним попыткам обращаются чаще. Артефакты после MVP получат другой хоткей.
- **Язык — `ctrl+l`.** `ctrl+l` не используется в полях ввода bubbles. Тему после MVP повесим на `ctrl+t`.
- **`L`: ссылки MR vs метки issue.** Хоткеи контекстные: в контексте MR (таб MRs, MR detail) `L` открывает список ссылок MR, в Issues после MVP `L` остаётся за метками issue. Метки MR после MVP получат другой хоткей.
- **Пайплайны «мои/все».** В макете Pipelines это `f`. Заменяем на общий `m` (`user=@me`).
- **`T` — To-Do.** Глобальный, как `p` и `F`: обрабатывается корнем, в полях ввода не действует. Ни в одном контексте не занят.
- **`x` в To-Do — «выполнено».** Как `x` close в Issues: действие над строкой, закрывающее её. `X` — то же для всех, с confirm.
- **`t` в To-Do — тип.** Свободен везде; `s` остаётся главным фильтром (state), как в других списках.
- **`d` в списке MR — Diff.** Как в макете. `d` «удалить» есть только в таблице переменных Run pipeline — другой контекст.
- **`n` в табе MRs — новый MR.** Как `n` в Pipelines и Tags.
- **`c` на вкладке Diff** — комментарий к строке под курсором; на заголовке файла, `@@` и строке треда — обычный комментарий к MR, как на других вкладках.

**Отличия от макетов (MVP):**

| Где | В макете | В MVP |
|---|---|---|
| Pipeline | `a` артефакты | убран |
| Issues | `n` новая, `L` labels, `A` assign, `b` ветка+MR | убраны |
| Project picker | `ctrl+s` star | убран |

Раскрытие запрашивает список только этой группы (несколько раскрытых подряд за 100 мс уходят одной пачкой); пока он идёт — строка `◐ загрузка…` под заголовком. Раскрытая группа без записей — заголовок и строка `нет открытых` / `нет пайплайнов`.

Запись — сразу после переключения, в фоне. Проекты, которых больше нет в workspace, при записи выбрасываются.
- **Запросы только по раскрытым.** Первое открытие таба, поллинг и `r` запрашивают списки только раскрытых групп (батчами, как раньше). Свёрнутые группы обновляют заголовки из обзора проектов: тик таба 60 с и `r` перезапрашивают и обзор (фазы 1 и 2, без тегов).
- **Счётчики табов.** `2 MRs 6` — сумма открытых MR из обзора проектов; в режиме фильтра — число найденных записей. У Pipelines число показывается только в режиме фильтра: без фильтров оно по свёрнутым группам не известно.
- **Фильтр проектов `P`** — оверлей выбора проектов (мульти-фильтр), без запросов к GitLab:
  - заголовок `Проекты · Pipelines  2 отмечено`, поле ввода и список GitLab-проектов workspace (не-GitLab строки не показываются): сначала отмеченные, затем остальные по активности; у строки `[x]`/`[ ]` и путь;
  - ввод сужает список локальным fuzzy по пути; `space` отмечает или снимает отметку с выбранной строки (в путях пробелов нет, в поле он не печатается); `ctrl+a` отмечает все видимые, а если все видимые уже отмечены — снимает с них отметку; `↓/↑`, `ctrl+n/ctrl+p`, `ctrl+d/ctrl+u`, `pgdown/pgup` — как в `p`;
  - `enter` применяет: есть отмеченные — в табе остаются только их группы, чип `проекты: 3 ✕` (для одного — `проект: platform/route-service ✕`); отмеченных нет, но есть текст — группы, путь которых совпал с текстом, чип `проект: route ✕`; нет ни того, ни другого — фильтр `P` снимается;
  - `esc` закрывает оверлей без изменений; повторный `P` открывает его с текущими отметками и текстом;
  - скрытые группы не меняют свёрнутость; в строке фильтров справа при активном `P` — `показаны 3 из 13 проектов`;
  - у MRs и Pipelines свой фильтр; через `f` в экран проекта не переносится;
  - **отмеченные проекты сохраняются** в `state.json` (5.8) на хост, workspace и таб и восстанавливаются при запуске; проекты, которых больше нет в workspace, выбрасываются, а если не осталось ни одного — фильтра нет. Текстовый вариант `P` не сохраняется. `backspace` сбрасывает `P` вместе с остальными фильтрами таба и стирает сохранённые отметки.
- **Режим фильтра.** Если в табе активен сужающий фильтр — MRs: текст `/`, `m` или state не `opened`; Pipelines: `status`, `ref` или `m`; Tags: текст поиска `/`, — запрос идёт по всем проектам workspace, прошедшим фильтр `P`, как до свёрнутых групп. Группы с результатами показываются раскрытыми, группы без результатов скрыты, в строке фильтров — `найдено в 4 проектах из 13` (13 — проекты, прошедшие `P`). Расширение `P` в этом режиме догружает только проекты, которые ещё не запрашивались, сужение запросов не делает. `space`/`enter` в этом режиме сворачивают группу только до сброса фильтров и в `state.json` не пишутся. Сброс сужающих фильтров (`backspace`) возвращает сохранённый набор раскрытых групп без нового запроса по свёрнутым.
- Группы рендерятся по мере прихода пачек GraphQL. Ещё не пришедшие — строкой `◐ platform/x загрузка…`.
- **MRs:** колонки IID, Title, Author, «Ты» (author/assignee/reviewer), Pipeline, Appr, Upd. Фильтр state (opened по умолчанию).
- **Строка фильтров табов:** «Проекты» — `/` локальный текстовый фильтр по имени папки и пути проекта без запросов; MRs — `state` и свободный текст (поиск по заголовку), `s` — цикл state; Pipelines — `status` и `ref`, `s` — цикл status; в обоих — фильтр проектов `P`. `backspace` сбрасывает фильтры таба (включая «я» и `P`). Подсказок с сервера в строке фильтров workspace нет.
- **Pipelines:** Status, ID, Ref, Source, Commit, Dur, Ago. Превью — стейджи выбранного пайплайна.
- **Tags** (M3): колонки и превью — как в табе Tags проекта (3.4); compare — с default-веткой из обзора, «n предложит» — по тегам группы. Сводка раскрытой группы — `58 тегов · показано 3` (`X-Total`), без тегов — `нет тегов`. Строка фильтров: `P`, «я: не применяется к тегам», `/ поиск`; справа `на проект: 3 · сорт: version ↓`. `/` — свободный текст (`search` на сервере), непустой включает режим фильтра; `s` не действует; `backspace` сбрасывает текст и `P`. Запросы — REST на проект (5.2), только по раскрытым группам; поллинг 60 с без быстрого тика.
- **Фильтр `m`:**
  - MRs — я автор, assignee или ревьюер;
  - Pipelines — `username = me`;
  - Tags — в строке фильтров «я: не применяется к тегам».
- **Действия:** `enter` открывает объект (MR detail / Pipeline / пайплайн тега). Действия над записями — те же, что в списках режима проекта, в контексте проекта строки: MRs — `a`, `M`, `b`, `c` (комментарий, 3.16), `C` (если у проекта есть локальная папка и найден glab), `d` (MR на вкладке Diff), `n` (новый MR, 3.18), `o` (список MR проекта с фильтрами таба), `O`, `y`; Pipelines — `l`, `n`, `R`, `c`, `o`, `O`, `y`; Tags (M3) — `n`, `D`, `y` (имя тега), `o` (страница тегов проекта, с поиском). `P` в списках нет: в строке пайплайна нет выбранной джобы. Для `n` в MRs, Pipelines и Tags берётся проект выбранной строки; `n` работает на любой строке группы, включая заголовок и «ещё N». У архивного проекта `n` в MRs недоступен. На заголовке группы и строке «ещё N» действия над записью недоступны.
- **`f`** с любой строки таба (запись, заголовок, «ещё N») — экран проекта на том же табе (2.7). Фильтры таба (state или status и «я», в Tags — текст поиска) переносятся в экран проекта; `backspace` в проекте их сбрасывает. Локальная папка — первая папка проекта в workspace.
- **Поллинг:** активный таб — раз в `polling.workspace` (60 с), только раскрытые группы (в режиме фильтра — все показанные) и обзор для заголовков свёрнутых. В Pipelines, пока в раскрытых группах есть running/pending, дополнительно раз в `polling.active` (3 с) перезапрашиваются только проекты с такими пайплайнами. MRs быстрого тика не имеют.
- **Ленивая загрузка:** таб грузится только при первом открытии (только раскрытые группы), дальше — из кэша с фоновым обновлением.

  4. описание в markdown (HTML переводится, как в комментариях MR), не выше половины превью, обрезка `…`; пустое — «нет описания»;
  5. `КОММЕНТАРИИ 2` и последние комментарии без системных заметок — сколько влезает целиком, каждый: `author · 1h` и тело не длиннее 6 строк; заметки — лениво для выбранного issue (последние 50), ответ для другого issue выбрасывается, ошибка — «комментарии недоступны» без тоста;
  6. `c — написать комментарий…`.
- **Действия:** `enter` (экран issue, 3.15), `c` (3.16), `x` (close с confirm «Закрыть issue #1318?», reopen — сразу; тост «Issue #1318 закрыт» / «открыт снова», перезагрузка), `o`, `O`, `y`. Архивный проект — `c` и `x` скрыты.

**Таб Tags** (макет `Tags`):

- **Колонки:** Tag, Commit (short SHA), Message (первая строка сообщения тега, у lightweight-тега — заголовок коммита; `◆ release`, если есть релиз), Pipeline (последний пайплайн тега: глиф и `#id`, нет — `—`), Ago (время коммита). Порядок — сервера, `order_by=version&sort=desc`; страница 20, подгрузка за 5 строк до конца.
- **Строка фильтров:** слева `/ поиск: v1.1`, справа `сорт: semver ↓`. `/` — ввод свободного текста без ключей и подсказок, `enter` — поиск на сервере (`search`) с первой страницы, `backspace` вне ввода сбрасывает поиск. `m` и `s` не действуют.
- **Счётчик и футер:** в табе — общее число тегов (`X-Total`); справа в футере — `6 / 58` (позиция / всего).
- **Пусто:** «Нет тегов»; с поиском — «Нет тегов по запросу «v9» · backspace — сбросить поиск».
- **Превью:**
  1. `v1.14.2 @ 9fa2c51 · release: v1.14.2 · protected` (`protected` — только у защищённого);
  2. `main опережает на 2 коммита · n предложит v1.14.3`: compare `from=<тег>&to=<default-ветка>` лениво, только для выбранного тега (ответ для другого тега выбрасывается); 0 коммитов — `main совпадает с тегом`, пока идёт — `◐ сравниваем…`, ошибка — `сравнение недоступно` без тоста. «n предложит» — вариант по умолчанию из 3.10 по загруженным тегам, только без активного поиска;
  3. `Release notes: <первая непустая строка описания релиза>`, если есть релиз.
- **Действия:** `n` (New tag, 3.10), `D` (удалить, confirm), `enter` (пайплайн тега; нет — тост «У тега нет пайплайна»), `y` (копировать имя тега), `o` (`<проект>/-/tags`, с поиском — `?search=<текст>`). Архивный проект — `n` и `D` скрыты.
- **Удаление:** confirm «Удалить тег v1.14.2?», описание «Тег удалится в GitLab, коммит 9fa2c51 останется.», у защищённого — плюс «Тег защищён: GitLab, скорее всего, откажет.». Успех — тост «Тег v1.14.2 удалён» и перезагрузка; 403 у защищённого — «Тег v1.14.2 защищён» (11.2).
- **Поллинг** — 30 с, курсор держится на теге по имени.

### 3.5. MR detail (макет `MRDetail`)

- **Шапка:** `platform/route-service › MRs › !479`.
- **Блок заголовка:** title, `author · source → target · открыт 1h назад · +48 −12 в 3 файлах`. Вместо «открыт …» по состоянию: смерженный — `смержил d.orlov 5ч назад` (без `mergeUser` — `смержен 5ч назад`), закрытый — `закрыт 3д назад`; время берётся из `MergedAt`/`ClosedAt`. Ссылки в title (`#12`, `!45`, `@anna.k`, `ABC-123`, URL) — OSC 8, текст не меняется (см. «Ссылки MR» ниже).
- **Чипы статуса:**
  - mergeable-статус из `detailed_merge_status`: `● mergeable`, `⚠ conflict`, `◐ ci_still_running`, `✗ not_approved`, `discussions_not_resolved` и т.д.; текст статуса не переводится, к нему добавляется понятная подпись; у merged/closed/locked MR вместо него чип состояния без подписи: `✓ merged`, `○ closed`, `○ locked`;
  - апрувы `✓ 1/2 approved`, при наборе и сверх нужного — `✓ 3 approved`;
  - пайплайн;
  - число неразрешённых тредов.
- **Вкладки** (`tab` переключает): Overview, Diff, Discussions, Pipelines, Commits — в этом порядке, как в макете. `d` в списке MR открывает экран сразу на Diff.
  - **Overview:** описание через glamour слева; ссылки GitLab в тексте (`#12`, `!45`, `@anna.k`, ключи трекера) и совпадения правил `links` — тоже OSC 8 (см. «Ссылки MR»). Справа колонка: APPROVALS, LABELS, PIPELINE (стейджи и джобы кратко), последний тред.
  - **Diff** (T35, [#27](https://github.com/4aykovski/glview/issues/27)): изменения MR одной прокруткой — файлы подряд, у каждого заголовок и ханки unified diff.
    - **Заголовок вкладки:** `Diff N`, N — число файлов загруженного диффа; до загрузки — `MergeRequest.Diff.Files` (`diffStatsSummary`), если известен, иначе без числа.
    - **Заголовок файла** (Bold, во всю ширину): `▾ internal/slots/alloc.go` (свёрнут — `▸`), справа `+30 −8` (числа — по строкам диффа файла). Переименование — `old/path.go → new/path.go`, новый файл — пометка `новый`, удалённый — `удалён`, сгенерированный (`generated_file`) — `сгенерирован` (Muted). Между файлами пустая строка.
    - **Строки ханка:** две колонки номеров (старый и новый, Muted, ширина — по самому длинному номеру в диффе), знак и текст: добавленная `+` (роль Success), удалённая `-` (роль Error), контекстная — пробел (обычный текст). Заголовок ханка `@@ -40,7 +40,9 @@ func …` — Muted во всю строку, без номеров. `\ No newline at end of file` — Muted, без номеров. Табы в тексте — 4 пробела. Длинные строки не переносятся: `←/→` сдвигают текст на 8 колонок (номера стоят на месте), сдвиг общий для всей вкладки. Без цветов (`NO_COLOR`) строки различаются знаком.
    - **Курсор** — строка (выделение `Selected`, как в таблицах): строка кода, заголовок ханка, заголовок файла или строка треда. `j/k` по строкам, `J/K` к заголовку следующего/предыдущего файла, `g/G`, листание. Свёрнутый файл — одна строка заголовка, курсор через него проходит.
    - **Сворачивание:** `space` на любой строке файла сворачивает или разворачивает файл (курсор встаёт на его заголовок), `z` сворачивает все, если хоть один развёрнут, иначе разворачивает все. По умолчанию свёрнуты сгенерированные файлы и файлы, у которых дифф скрыт сервером. Выбор пользователя держится по пути файла при обновлении.
    - **Дифф скрыт сервером** (`too_large` или `collapsed`, пустой `diff`): заголовок с пометкой `слишком большой`, тело при развороте — строка «дифф скрыт GitLab — o откроет файл в браузере». Пустой `diff` без этих флагов (бинарный файл, смена режима, переименование без правок) — строка «нет текстового диффа».
    - **Треды на строках:** diff-треды (`Discussion.Position`, тред не устаревший — строка нашлась в текущем диффе: по `new_path` и `new_line`, у удалённой строки — по `old_path` и `old_line`, и SHA позиции `head_sha` совпадает с `MergeRequest.DiffRefs.HeadSHA`; пока `DiffRefs` или `head_sha` позиции не известны — по строке одной) показываются под своей строкой — по строке на тред с отступом под колонками номеров: `● anna.k · 2h · Давай метрику с лейблом зоны… · 1 ответ` (`●` Warning у неразрешённого, `✓` Muted у разрешённого; первая строка тела первой заметки без markdown, обрезка `…`). `enter` на ней — тред на вкладке Discussions (см. «Переход с Diff»). Треды, строку которых не нашли или чей `head_sha` не совпал с текущим (после пуша или force-push номера строк относятся к другой версии и указали бы на чужой код), на Diff не показываются, они есть в Discussions.
    - **Комментарий к строке** `c` на строке кода (`+`, `-`, контекст) — форма комментария (3.16) с заголовком `Комментарий · !479 · internal/slots/alloc.go:42` (номер — новый, у удалённой строки — старый) и позицией строки. Отправка — новый тред с позицией (5.2: `new_line` у добавленной, `old_line` у удалённой, оба у контекстной; `old_path`/`new_path` файла; SHA — `MergeRequest.DiffRefs`). На прочих строках, а также пока `DiffRefs` не известен, `c` — обычный комментарий к MR. После отправки discussions перезапрашиваются, новый тред появляется под строкой. Ответ 400 (строка ушла из диффа, MR обновился) — тост с текстом GitLab и подсказкой «обнови (r)», текст формы сохраняется (как при любой ошибке 3.16).
    - **Ссылки `o`/`y`:** `<ссылка MR>/diffs#<sha1(new_path)>` — файл под курсором (якорь файла в вебе GitLab); до загрузки или на пустом диффе — `<ссылка MR>/diffs`.
    - **Загрузка лениво**, по тем же правилам, что Commits: при первом переходе на вкладку (или при открытии через `d`), дальше — по `r` и при смене head SHA MR; тики поллинга дифф не запрашивают. Ключ кэша содержит head SHA, поэтому после пуша в MR старый дифф из кэша не берётся (ответ `/diffs` SHA не несёт, сверять не с чем). Пока идёт — `◐ загружаем дифф…`; пусто — «Нет изменений»; ошибка — тост, повтор по `r` или повторному входу на вкладку. Курсор при обновлении держится на том же файле и номере строки, если они остались.
    - **Футер:** `j/k строка · J/K файл · space свернуть · c к строке · ←/→ сдвиг · o браузер`; на строке треда вместо `c к строке` — `enter тред`.
  - **Discussions:** треды карточками: каждый тред — рамка во всю ширину (неразрешённый — цвет Warning, разрешённый и неразрешаемый — Border, текущий — толстая рамка `┏━┓` цвета Accent: форма отличает его и там, где Accent и Warning совпадают или цветов нет), между карточками пустая строка. Внутри: у каждой заметки строка-заголовок (автор жирным, время Muted; у первой — статус треда `● unresolved`/`✓ resolved` и `путь:строка` для diff-тредов, без диффа), тело в markdown, между заметками тонкая линия, ответы с отступом. Системные заметки не показываются. Только чтение.
    - **HTML в комментариях:** перед рендером тело переводится в markdown (боты пишут HTML): `<table>` — таблица, `<br>` — перенос, `<details><summary>X` — `▸ X` и содержимое, `<b>/<i>/<code>/<a href>` — разметка, прочие теги вырезаются с сохранением текста; соседние ячейки не склеиваются.
    - **Сворачивание:** свёрнутый тред — одна строка: заголовок первой заметки, её первая строка текста и `N ответов`. По умолчанию свёрнуты разрешённые треды и треды с телом первой заметки длиннее 20 строк; выбор пользователя сохраняется при обновлении данных.
    - **Переход с Diff:** `enter` на строке треда во вкладке Diff переключает на Discussions, делает этот тред текущим, разворачивает его и прокручивает к нему.
  - **Pipelines:** пайплайны MR, `enter` → Pipeline.
  - **Commits:** коммиты MR таблицей: short SHA (Accent), заголовок коммита (тянется), автор (`AuthorName`), «когда» (`CreatedAt`, относительное время). Порядок — как отдаёт API, новые сверху (как в вебе); клиент не пересортировывает.
    - **Заголовок вкладки:** `Commits N`. N — длина загруженного списка, если список соответствует текущему head SHA MR (первый коммит списка == `MergeRequest.SHA`, или SHA неизвестен, или список пуст); иначе `MergeRequest.CommitCount` из деталей MR, если он больше 0; иначе длина списка. До загрузки — `CommitCount`, если он больше 0, иначе без числа. Так после пуша в MR счётчик не отстаёт, даже если перезапрос коммитов упал.
    - **Загрузка лениво:** при первом переходе на вкладку. Дальше перезапрос (принудительный, мимо кеша) только при `r` и когда head SHA MR (`MergeRequest.SHA` из очередного ответа деталей) отличается от SHA последнего запроса коммитов; тики поллинга сами коммиты не запрашивают. По `r` (и после восстановления авторизации) коммиты перезапрашиваются после ответа деталей MR — один раз и уже под новый SHA; при ошибке деталей MR — тоже один раз. Пока вкладку не открывали, ни `r`, ни смена SHA коммиты не запрашивают. Ответ из кеша (не принудительный), у которого первый коммит не совпадает с текущим head SHA MR, сразу перезапрашивается принудительно — один раз; принудительный ответ принимается как есть (без цикла, если API отстаёт). После ошибки перезапроса тики с тем же SHA коммиты не долбят — ждут `r`, повторного входа на вкладку или нового SHA.
    - **Загрузка, пусто, ошибка** — как на вкладке Pipelines: строка загрузки в таблице, `Нет коммитов` / `No commits`, ошибка — тостом; после ошибки повторный переход на вкладку или `r` запрашивают снова.
    - **Клавиши:** `j/k`, `g/G`, листание — как в других таблицах; `enter` ничего не делает (дифф отдельного коммита — не цель, раздел 1) и в футере не показывается; `o` — выделенный коммит в браузере, `y` — копировать его ссылку. Пока список пуст или не загружен, `o`/`y` работают со ссылкой MR.
    - **Ссылка коммита:** `CommitSummary.WebURL` (поле `web_url` ответа REST). Если оно пустое — ссылка MR, как при пустом списке.
    - **Колонка «когда»** (здесь и на Pipelines) пересчитывается при каждом ответе деталей MR, то есть раз в цикл поллинга, а не только при загрузке списка; выделенная строка при этом не сбрасывается.
- **Ссылки MR:**
  - **Источники:**
    - `TitleLinks`/`DescriptionLinks` — `<a href>` из GraphQL `titleHtml`/`descriptionHtml`: в них GitLab уже проставил ссылки на `#12`, `!45`, `@user`, URL и ключи внешнего трекера, если интеграция настроена в проекте. Из HTML берутся только `href` и текст ссылки (пробелы схлопнуты, сущности раскрыты). Пропускаются ссылки без текста, якоря заголовков (`href="#…"`) и схемы кроме `http(s)` (`mailto:` и т. п.); относительный `href` (`/anna.k`, `/platform/route-service/uploads/…`) дополняется origin'ом инстанса (схема + хост; path-prefix GitLab уже пишет в `href`). Только в деталях MR (`MRDetail`), не в `MRRow`;
    - правила `links` конфига (раздел 7) по тексту title и description (description — markdown-источник как есть);
    - голые `http(s)://` в title и description; хвостовая пунктуация `.,;:!?` и непарные закрывающие `)]}>'"` в ссылку не входят.
  - **Общий список:** сначала ссылки title, потом description. Внутри каждого — по позиции первого вхождения текста ссылки в исходный текст; не найденные — в конце, в порядке HTML. Дубли по URL схлопываются, остаётся первое вхождение. При одинаковом тексте с разными URL ссылка из HTML GitLab важнее правил, правила — в порядке конфига.
  - **OSC 8** (cmd/ctrl+клик открывает в браузере) накладывается на уже отрисованный текст:
    - вхождение текста ссылки ищется по видимому тексту без учёта ANSI-стилей, целым токеном (соседние символы — не буква, не цифра и не `_`), в пределах одной строки;
    - участки, уже лежащие внутри OSC 8 (ссылки glamour), не трогаются; при пересечении вхождений побеждает более длинный текст;
    - видимый текст не меняется: терминал без OSC 8 показывает то же, что раньше, golden-снимки (простой текст) не меняются;
    - ссылка, разорванная переносом строки или обрезанная `…`, не кликабельна — она есть в оверлее `L`.
  - **Где:**
    - MR detail — title и описание на Overview: все источники;
    - таб MRs (режим проекта и workspace) — колонка Title и title в превью: только правила `links` и голые URL (`MRRow` без `titleHtml`, раздел 5.2); в ячейке таблицы OSC 8 накладывается после обрезки по ширине;
    - треды Discussions — без изменений.
  - **Оверлей `L`** — для терминалов, где клик не работает (tmux без `terminal-features hyperlinks`, терминал без OSC 8):
    - рамка списочных оверлеев (`p`, `F`, `P`) без поля ввода: заголовок `Ссылки · !479` / `Links · !479`, строки `текст — URL` (URL — Muted, обрезка `…` справа; если текст совпадает с URL — только URL), справа в футере `3/7`;
    - `j/k` `↓/↑` `ctrl+n/ctrl+p` — ход, `g/G` — начало/конец, `enter` — открыть в браузере и закрыть оверлей, `y` — скопировать URL (тост «Скопировано: ссылка») и закрыть, `esc` — закрыть;
    - обновление MR при открытом оверлее перестраивает список, выделение держится по URL;
    - **MR detail:** список из текущих деталей MR;
    - **таб MRs:** на строке MR (на заголовке группы и «ещё N» в workspace недоступен). `L` запрашивает детали выделенного MR (`MergeRequests().Get` — тот же запрос, что у MR detail; msg с `Gen`; ответ для другого MR или старого поколения выбрасывается) и открывает оверлей по ответу. Ошибка запроса — тост ошибки; если по `MRRow` (правила и голые URL в title и description) ссылки есть, оверлей открывается с ними;
    - **ссылок нет** — оверлей не открывается, тост «В MR нет ссылок» / «No links in the MR».
- **Действия:** `a`, `M`, `b`, `C`, `L`, `o`, `y`, `c` (комментарий к MR, 3.16; на Diff — к строке; после отправки discussions перезапрашиваются). `o`/`y` на Discussions — текущий тред, на Commits — выделенный коммит, на Diff — файл под курсором, на остальных вкладках — MR.
- **Перепроверка `unchecked`:** GitLab считает `detailed_merge_status` лениво, чтение через GraphQL пересчёт не запускает, и открытый MR может долго висеть в `unchecked`. Если у открытого MR (state opened) статус `unchecked`, экран один раз за время жизни на ключ `iid@sha` просит GitLab пересчитать его (`RecheckMergeStatus`); ответ `checking` сразу обновляет чип. Пока статус `unchecked`/`checking`/`preparing`, MR опрашивается раз в `polling.active` (3 с), но не дольше 60 с с момента запроса; потом обычный интервал. Ошибка перепроверки (в т.ч. нет прав) пользователю не показывается, только debug-лог. Список MR не перепроверяет.
- **Поллинг:** пока экран на вершине — 3 с при running-пайплайне, rebase в процессе или перепроверке статуса (до 60 с), иначе 30 с.

### 3.6. Merge dialog

- **Поля (свои контролы оверлея, не huh — нужен `enter` = «подтвердить» с любого поля; `←/→` способ, `space` чекбоксы, `j/k` по полям):**
  - способ: «Merge сейчас» | «Merge, когда пайплайн пройдёт» (auto-merge);
  - `[ ] squash` — по умолчанию по настройке проекта или MR;
  - `[x] удалить source-ветку` — по умолчанию из `force_remove_source_branch`;
  - сообщение коммита скрыто, используется дефолтное.
- **Доступность:** если `detailed_merge_status` не `mergeable` и не `ci_still_running`/`ci_must_pass`, диалог показывает причину и кнопка неактивна.
- **Подтверждение:** диалог сам является confirm-модалкой: `enter` подтверждает, `esc` отменяет.
- **Защита от гонки:** передаём `sha` = head SHA, который видели. На 409 — тост «в ветку запушили, обнови (r)».

### 3.7. Pipeline (макет `Pipeline`)

- **Шапка:** статус, `#91840 on feat/surge · a91f2c0 commit title`, вторая строка — `anna.k · merge_request !482 · 3m40s · 9 джоб: 4 ✓ 2 ◐ 1 ► 2 ○`.
- **Стейджи — колонки** в порядке пайплайна, внутри джобы со статусом и длительностью.
  - Bridges (trigger-джобы) показываются в своём стейдже с глифом `⇢`. Если есть downstream-пайплайн, в отдельной колонке «downstream» — `⇢ qa/e2e-routes  ◐ running`.
  - Колонки растягиваются на ширину экрана: `w/n`, но не уже 25 символов; остаток ширины достаётся последней колонке. Ref в шапке показывается как `!<iid>` для MR-пайплайнов.
  - Если стейджей больше, чем влезает, колонки скроллятся горизонтально, активная всегда видна.
- **Панель выбранной джобы:** имя, `job #id · stage`, runner, длительность, `allow_failure`, попытки, последняя непустая строка лога (только у running/failed, ленивый запрос).
- **Попытки джобы.** После retry у джобы несколько попыток: последняя показывается в колонке, прежние — в `Job.Attempts`.
  - В панели строка `попытки: #305 ✓ · #303 ✗ · #302 ✗`, новые первыми; что не влезло по ширине — `+N`. Строки нет, если попытка одна.
  - `a` открывает оверлей со списком попыток: `#id статус длительность время старта`, последняя отмечена «последняя». `j/k` выбор, `enter` — Job log выбранной попытки, `esc` закрыть. Лог получает попытки джобы по состоянию экрана на момент `enter`: если поллинг, пока открыт оверлей, принёс новую попытку, она в логе последняя. На джобе без прежних попыток и на bridge `a` ничего не делает и не показывается в футере.
- **Действия:**
  - `enter` — Job log последней попытки; на bridge — Pipeline downstream-пайплайна;
  - `a` — попытки джобы (см. выше);
  - `P` — play manual: форма переменных, пустая форма = play без переменных. Фокус: таблица → кнопка «Запустить» (`tab`/`shift+tab`), `enter` на кнопке запускает, `esc` отменяет — как в Run pipeline (3.9);
  - `R` — retry джобы (retry всего пайплайна — `R` в списке пайплайнов);
  - `c` — cancel джобы;
  - `o` — пайплайн в браузере, `O` — выделенная джоба (на bridge с downstream — downstream-пайплайн), `y` — ссылка на пайплайн.
- **Поллинг:** 3 с, пока пайплайн не в финальном статусе.

### 3.8. Job log (макет `JobLog`)

- **Шапка:** `#91840 › test:integration ◐ running 1m12s`, справа `● follow · 1 284 строк · обновл. 2s`.
- **Viewport с номерами строк.** Секции:
  - заголовок секции — `▸ name` (свёрнута) или `▾ name` (развёрнута), справа длительность;
  - секции с `[collapsed=true]` изначально свёрнуты.
- **ANSI SGR сохраняются**, прочие escape-последовательности вырезаются (раздел 5.6).
- **Follow-режим:**
  - включён по умолчанию у running-джобы;
  - viewport прилипает к концу;
  - ручной скролл вверх выключает follow, `f` или `G` включают обратно.
- **Поиск `/`:** подстрока без учёта регистра. Совпадения подсвечиваются, `n/N` переходят по ним, свёрнутые секции с совпадением раскрываются. Строка поиска показывает «совпадение 1 из 3».
- **Длинные строки** не переносятся, горизонтальный скролл `←/→`.
- **Попытки:** если у джобы больше одной попытки, в шапке после длительности — `· попытка 2/3` (у последней — `3/3`).
  - `a` открывает тот же оверлей попыток, что в Pipeline; `enter` показывает выбранную попытку **на этом же экране** (лог не кладётся в стек поверх, `esc` возвращает туда, откуда лог открыт).
  - `[` — предыдущая (более старая) попытка, `]` — следующая (более новая); на крайней попытке клавиша ничего не делает.
  - При смене попытки сбрасываются поиск, свёрнутость секций и скролл, как после `R`. Follow и поллинг — по статусу показанной попытки: у прежней (она всегда в финальном статусе) follow выключен, лог запрашивается один раз; у последней — как обычно.
  - Откуда список попыток: из Pipeline передаётся вместе с джобой. Если лог открыт иначе (`l` в списке пайплайнов), при открытии один раз запрашивается пайплайн — всегда свежий (`Pipelines().Get` без кеша; финальный пайплайн кладётся под ключ кеша экрана Pipeline). После `R` новая джоба становится последней попыткой, список дополняется без запроса; после `c` у отменённой попытки в списке обновляется статус.
- **Действия:** `R` retry (открывает лог новой джобы), `c` cancel, `o`. В логе прежней попытки `R` и `c` действуют на последнюю попытку этой джобы, `o` открывает в браузере ту попытку, лог которой на экране.
  - `R` и `c` сбрасывают кеш пайплайна и списка пайплайнов (как те же действия на экране Pipeline); экран Pipeline под логом при возврате перечитывает пайплайн, не дожидаясь поллинга.

### 3.9. Run pipeline (макет `RunPipeline`)

Модальная форма: два блока и кнопка «Запустить». `tab` переводит фокус по кругу ref → переменные → кнопка, `shift+tab` — обратно (пока ячейка в редактировании или открыт список, `tab` не действует).

1. **Ref.** Текстовое поле с автодополнением: ветки и теги (`search` с debounce 300 мс, до 20 веток и 20 тегов на запрос).
   - **Стартовое значение** (конфиг `run_pipeline.prefill_local_branch`, раздел 7):
     - `true` (по умолчанию) — в поле текущая локальная ветка, в подсказках она первая с пометкой «текущая в git», независимо от `refs_first`. Нет локальной ветки (detached HEAD, нет клона) — в поле default-ветка, порядок по `refs_first`.
     - `false` — поле пустое, порядок по `refs_first`; локальная ветка стоит в группе веток на общих основаниях, но с пометкой «текущая в git».
   - **Подставленное значение не фильтрует.** Первый поиск при открытии идёт с пустым запросом: видны все ветки и теги, курсор на подставленной ветке. Подставленная ветка всегда есть в списке: если её нет в ответе (лимит 20 на запрос), она добавляется первой в группу веток. Поэтому `enter` сразу после открытия оставляет в поле подставленную ветку, а не первую строку ответа. Подставленный текст ведёт себя как выделенный: первый печатный символ заменяет его целиком, `backspace` стирает целиком, стрелки `←/→`, `home`, `end` снимают выделение и дают править текст. После любой правки поле фильтрует как обычно.
   - **Порядок групп** — конфиг `run_pipeline.refs_first`: `branches` (по умолчанию) — сначала ветки, потом теги; `tags` — наоборот. Внутри группы — порядок ответа API.
   - **Список подсказок** — окно из 6 строк (на низком терминале меньше — форма целиком помещается в экран, от 80×24), прокручивается за курсором: выбранная строка всегда видна, `enter` подставляет именно её. `pgdown`/`pgup` — курсор на первую строку следующей/предыдущей группы. Под окном строка-сводка: `ветки 20+ · теги 7 · 3/27` (`20+` — ответ упёрся в лимит запроса; `3/27` — позиция курсора). Так теги видны, даже если не влезли в окно.
   - **Поиск идёт**, пока не пришли оба ответа (ветки и теги) последнего запроса: до этого рядом со сводкой «ищем…». Список подсказок заменяется целиком, когда пришли оба ответа; до этого остаётся список предыдущего запроса. Ответы двух разных запросов в одном списке не смешиваются. Ответы устаревших запросов выбрасываются.
   - **Ошибка запроса** веток или тегов: группа этого вида пустеет (старый список не остаётся), тост с ошибкой (как `Env.Fail`), второй вид показывается как есть. Если упали оба — один тост, в списке «нет ссылок: ошибка запроса».
2. **Переменные.** Таблица `KEY | VALUE | type`.
   - Фокус на таблице, но не в ячейке: `a` — добавить строку, `d` — удалить, `enter` — редактировать ячейку, `h/l` `←/→` — ячейка, `j/k` `↓/↑` — строка, `space` — сменить тип.
   - **Выбранная ячейка видна всегда**, в том числе пустая: подсветка выбора (`Styles.Selected` или аналог из `common.Styles`) на всю ширину колонки. Пустая ячейка показывает приглушённый плейсхолдер, как в макете: `KEY`, `value`.
   - **Редактирование:** каретка видна сразу после `a` или `enter`, без лишних нажатий. Ширина поля ввода в ячейке следует за шириной колонки, в том числе если терминал изменил размер во время правки: каретка в конце значения не обрезается. `enter` сохраняет ячейку (у новой строки после ключа — переход к значению), `esc` отменяет ввод (новая строка без ключа удаляется).
   - Тип: `env_var` | `file`.
   - **Пустая таблица:** «переменных нет — `a` добавить».
   - **Подсказки** под таблицей: «Из .gitlab-ci.yml: 1 DEPLOY_ENV [staging, prod-canary], 2 SKIP_E2E». `1`–`9` — добавить подсказку с этим номером. `s` — список всех подсказок (нужен, когда их больше девяти): ключ, `valueOptions`, `description`; `j/k` ход, `enter` добавить, `esc` закрыть. Подсказок больше, чем влезает в строку, — строка обрезается `…` и заканчивается «`s` все (N)».
   - Выбор подсказки добавляет строку (или меняет значение строки с тем же ключом). Для `valueOptions` значение выбирается из списка.
   - Подсказки загружаются один раз на ref: если `enter` в списке ref выбрал тот же ref, для которого подсказки уже загружены или грузятся, повторного запроса нет и подсказки не пропадают.

Макет предлагает `ctrl+a`/`ctrl+d` — они конфликтуют с readline-сочетаниями в полях ввода, поэтому заменены на `a`/`d` вне режима редактирования.

- **Строка хоткеев** внизу формы зависит от фокуса:
  - ref: `↑/↓ ref · pgdn/pgup группа · enter выбрать · tab дальше · esc отмена`;
  - таблица: `a добавить · d удалить · enter изменить · space тип · 1-9/s подсказка · tab дальше · esc отмена`;
  - кнопка: `enter запустить · tab дальше · esc отмена`;
  - ячейка в редактировании: `enter сохранить · esc отменить ввод`;
  - список значений или подсказок: `j/k выбор · enter взять · esc закрыть`.
- **Предпросмотр:** «будет создан: ref=feat/surge, variables=2».
- **Запуск:** `enter` на кнопке «Запустить». Кнопка в фокусе — активный стиль, без фокуса — обычный; подпись `enter Запустить`, как в макете. Отдельного сочетания нет: `ctrl+s` занят у пользователей tmux (и flow control терминала), а `ctrl+enter` терминалы не различают. Это и есть подтверждение, отдельной confirm-модалки нет: форма уже явный шаг. Исключение — тег с пайплайном, ниже.
- **Тег, у которого уже есть пайплайн.** Тег ли ref, решает только точный поиск `GET /repository/tags?search=^<ref>$` (в ответе есть тег с этим именем). Загруженные подсказки для этого не используются: они отфильтрованы, урезаны лимитом и могут быть от прошлого запроса. Не тег — создание сразу. Если ref — тег, перед созданием запрашивается `GET /projects/:id/pipelines?ref=<ref>&scope=tags&per_page=1`. Есть пайплайн — confirm-модалка (3.14): «Запустить ещё один пайплайн на теге v1.14.2?», описание «У тега уже есть пайплайн #91761 (success). Новый пойдёт на том же коммите: джобы тега — сборка, публикация, деплой — выполнятся снова.», по умолчанию «Отмена». Пайплайна нет — создание сразу. Проверка упала — та же модалка с описанием «Не удалось проверить, есть ли у тега пайплайн: <ошибка>».
- **Снимок при запуске.** `enter` на кнопке запоминает ref и переменные. Проверка тега, confirm-модалка и создание работают с этим снимком, а не с тем, что в форме сейчас.
- **Блокировка на время запуска.** Пока идёт проверка тега или создание, форма заблокирована: ref и переменные не меняются, фокус не переходит, повторный `enter` игнорируется. В строке хоткеев — «проверяем тег… · esc отмена» или «создаём…». `esc` во время проверки прерывает её: ответ выбрасывается, форма снова редактируется. Во время создания `esc` не действует: запрос уже ушёл, ждём ответ (не дольше таймаута запроса).
- **Ответы закрытой формы.** Все запросы формы (поиск ref, подсказки, проверка тега, создание) несут поколение формы с уникальным id экземпляра (`common.Gen`, раздел 6.4). Ответ, пришедший после закрытия формы, выбрасывается и не попадает в новую форму Run pipeline, открытую позже.
- **После создания** сразу открывается экран нового пайплайна.

### 3.10. New tag (макет `Tags`, форма справа)

Модальная форма (как Run pipeline), заголовок `Новый тег · platform/route-service`.

- **Имя.** Select: `v1.14.3 (patch)` (по умолчанию), `v1.15.0 (minor)`, `v2.0.0 (major)`, плюс «своё…» с текстовым полем (начальное значение — вариант по умолчанию). Под полем — `предложено: patch от v1.14.2` и строка вариантов, текущий выделен. `↑/↓` в фокусе имени меняют вариант (и в режиме «своё…»). Сочетания `ctrl+n`/`ctrl+j` из макета не используем: `ctrl+j` в терминале — это Enter. Варианты считает `internal/semver` по 100 тегам (`order_by=version`), запрошенным при открытии формы; пока они не пришли — `◐ загружаем теги…`, ошибка — тост и только «своё…». Правила — 11.2 («Нет semver-тегов», «Последний тег — prerelease»).
- **Из ref:** по умолчанию default-ветка, автодополнение веток (`search` через 300 мс, до 5 подсказок под полем, `↑/↓` выбор, `enter` подставить). Подпись `main @ 0b7d3e9 · 2 коммита после v1.14.2` из compare `<последний тег>…<ref>` (через 300 мс после смены ref): SHA — последний коммит `to`, число — коммиты диапазона. Тегов нет — `main · первый тег проекта`; ошибка — `ref не найден или сравнение недоступно`.
- **Сообщение (annotated):** необязательное; если заполнено, создаётся annotated-тег, пустое — lightweight. По умолчанию `release: <имя>` и следует за именем, пока его не правили.
- **«В теге окажутся»:** до 10 коммитов из того же compare, новые сверху, больше — `… ещё N`; 0 — «нет новых коммитов после v1.14.2».
- **Фокус и кнопка:** внизу `esc отмена` и кнопка `enter Создать`. Фокус по кругу `tab`/`shift+tab`: имя → ref → сообщение → кнопка. `enter` в имени и сообщении — следующее поле, в ref — подставить подсказку (если список виден), иначе следующее поле. Создание — только `enter` на кнопке (как в Run pipeline); кнопка в фокусе — активный стиль.
- **Проверка:** пустое имя — «укажи имя тега»; имя уже есть среди тегов формы — «тег v1.14.2 уже есть»; пустой ref — «укажи ref». Ошибка — строкой над кнопкой, фокус в поле с ошибкой.
- **Создание:** `enter` на кнопке запоминает снимок (имя, ref, сообщение, SHA) → confirm-модалка «Создать тег v1.14.3 на main @ 0b7d3e9?» (SHA неизвестен — «на main?»), описание «Annotated-тег: «release: v1.14.3»» или «Lightweight-тег без сообщения», по умолчанию «Отмена» → создание со снимком. Пока идёт создание, форма заблокирована, в строке хоткеев «создаём…», `esc` не действует. Успех — форма закрывается, тост «Тег v1.14.3 создан», список перезагружается, курсор на новом теге. Ошибка — тост (у 400 — сообщение GitLab), форма остаётся с теми же значениями.
- **Ответы закрытой формы** выбрасываются: все запросы несут поколение формы (`common.Gen`, 6.4).

### 3.11. Project picker `p` (макет `ProjectPicker`)

- **Оверлей.** Fuzzy-поиск без сети. Секции: ИЗ GIT REMOTE (текущий), WORKSPACE (проекты верхнего Workspace стека), STARRED, НЕДАВНИЕ.
- **В строке:** путь, `★`, число открытых MR и активность, если известны из кэша.
- **Действия:** `enter` → режим проекта над верхним Workspace стека или над стартовым корнем (2.6), `esc` закрыть.
- **Навигация по списку:** `↓/↑`, `ctrl+n/ctrl+p`; `ctrl+d`/`ctrl+u` и `pgdown`/`pgup` — на полстраницы видимого списка (секции и заголовки считаются строками). Эти клавиши обрабатывает оверлей, а не поле ввода: `ctrl+u` не стирает введённое, `ctrl+d` не удаляет символ.

### 3.12. Global search `F`

- **Оверлей:** поле ввода и два раздела, «Проекты» и «Группы».
- **Запрос:**
  - пока в поле меньше 3 символов, ничего не ищем (GitLab не ищет совпадения короче 3 символов);
  - сразу показываем локальные fuzzy-совпадения из источников picker'а;
  - через 300 мс после последнего ввода — серверный запрос; результаты подмешиваются без дублей, локальные помечены.
- **Действия:** `enter` на проекте → режим проекта; `enter` на группе → workspace из проектов группы (`GroupSource`) над стартовым корнем: `esc` возвращает к исходному workspace или проекту (2.6).
- **Навигация по списку** — как в `p`, включая `ctrl+d`/`ctrl+u`.

### 3.13. Help `?`

- **Оверлей:** все хоткеи текущего экрана по группам (из `KeyMap()`), внизу — глобальные.
- **Состояние:** текущий язык и подсказка `ctrl+l`; статус glab («glab: найден, вошли на gitlab.example.com» / «glab не найден»).

### 3.14. Confirm-модалка

- **Состав:** заголовок, описание объекта, кнопки «Да» и «Отмена» (по умолчанию «Отмена»). `y`/`enter` на «Да» подтверждает, `n`/`esc` отменяет.
- **Где используется:** merge (3.6), cancel пайплайна и джобы, delete tag, rebase, close issue, создание тега, pull (10.4), запуск пайплайна на теге, у которого уже есть пайплайн (3.9), «отметить все To-Do выполненными» (3.17), замена правленого описания шаблоном и открытие уже существующего MR из ветки (3.18). В остальных случаях Run pipeline и play job используют свою форму как подтверждение.


### 3.15. Issue (макет `Issues`, полноэкранно)

- **Шапка:** `platform/route-service › Issues › #1318`.
- **Тело — одна прокрутка:** title (Bold), строка статуса (как в превью 3.4), `Labels: bug · pricing`, связанные MR по строке (всегда отдельным запросом `related_merge_requests`, без проверки `merge_requests_count`), разделитель, описание в markdown, `Комментарии N`, треды карточками — тот же вид и правила, что во вкладке Discussions MR detail (3.5: рамки, системные заметки скрыты, сворачивание по умолчанию, HTML → markdown). Код карточек общий (`screens/threads`). Нет тредов — «Комментариев нет · c — написать».
- **Клавиши:** `j/k`, `pgdown/pgup`, `ctrl+d/ctrl+u`, `g/G` — прокрутка; `J/K` — следующий/предыдущий тред (толстая рамка Accent, прокрутка к нему); `space` — свернуть/развернуть текущий тред; `c` — комментарий; `x` — close/reopen; `o` — issue в браузере; `y` — ссылка issue; `esc` — к списку с тем же курсором.
- **Данные:** `GET /issues/:iid`, `GET /issues/:iid/discussions` (все страницы), связанные MR; поллинг 30 с на вершине стека, `r` — мимо кэша; прокрутка и свёрнутость тредов сохраняются. После комментария — перезапрос и прокрутка к последнему треду.

### 3.16. Комментарий (оверлей Comment)

Общая форма для `c` в Issues (таб и экран issue) и в MR (таб MRs проекта и workspace, MR detail; на вкладке Diff — к строке кода, 3.5).

- **Вид:** модалка, заголовок `Комментарий · #1318 Surge coefficient ignores zone overrides` (MR — `!479 …`); многострочное поле (markdown как есть, высота от 6 строк до половины экрана); подсказка `markdown · tab — к кнопке · alt+enter — отправить`; низ — `esc закрыть` и кнопка `enter Отправить`.
- **Клавиши:** `tab`/`shift+tab` — поле ↔ кнопка. В поле `enter` — перенос строки, `alt+enter` — отправить (если терминал передаёт; основной путь — кнопка). На кнопке `enter` — отправить. `ctrl+s` не используем (tmux, flow control), `ctrl+enter` терминалы не различают.
- **Пустой текст** (одни пробелы) не отправляется: «комментарий пуст».
- **Отправка:** форма заблокирована, «отправляем…», `esc` не действует. Успех — форма закрыта, тост «Комментарий добавлен», экран перезапрашивает комментарии; ошибка — тост, форма остаётся с текстом.
- **Черновик:** `esc` закрывает без отправки, текст хранится в памяти до конца сессии (ключ — хост, проект, issue/MR, IID; у комментария к строке — ещё путь и номера строки); повторный `c` восстанавливает, успешная отправка стирает. На диск не пишется.
- **К строке кода:** заголовок `Комментарий · !479 · internal/slots/alloc.go:42`, отправка — `MergeRequests().CommentLine` с позицией (5.2) вместо `Comment`; остальное — как выше.
- **Ответы закрытой формы** в новую форму не попадают (`common.Gen`, 6.4).

### 3.17. To-Do (T36, [#28](https://github.com/4aykovski/glview/issues/28))

Список задач To-Do текущего пользователя — по всему инстансу, а не по проекту или workspace. Макета нет: раскладка — как у таба Issues (3.4).

- **Открытие:** `T` с любого экрана (2.6). Шапка: `To-Do · gitlab.example.com`, справа — как у всех экранов. Табов нет.
- **Строка фильтров:** `state:pending  type:any`, справа `5 из 12` (загружено / `X-Total`). `s` — state по кругу pending (по умолчанию) → done; `t` — type по кругу any → MR (`MergeRequest`) → issue (`Issue`); `backspace` — сброс к умолчаниям. `m` не действует (список и так «мой»). Свободного текста нет: API его не ищет.
- **Колонки** (по приоритету): Target (`!479`, `#1318`; коммит — short SHA; прочие типы — `—`), Title (заголовок цели, тянется), Action (подпись причины, переведённая; неизвестный `action_name` — как есть), Ago (`created_at`, относительное), Author, Project (путь проекта; у задач без проекта — `—`). Порядок — сервера (новые первыми); страница 20, подгрузка за 5 строк до конца; курсор держится по ID задачи.
- **Подписи Action** (en / ru): `assigned` — assigned / назначен; `mentioned` — mentioned / упоминание; `directly_addressed` — addressed / обращение; `review_requested` — review requested / ревью; `review_submitted` — review submitted / ревью оставлено; `approval_required` — approval required / нужен апрув; `build_failed` — pipeline failed / пайплайн упал; `unmergeable` — unmergeable / нельзя смержить; `merge_train_removed` — removed from train / убран из train; `marked` — added / добавлено; `member_access_requested` — access requested / запрос доступа.
- **Превью** (снизу, как у MRs; при ширине от 140 — справа, как у Issues):
  1. title цели (Bold);
  2. `!479 · platform/route-service · opened · 2h` (состояние цели — как есть, без перевода);
  3. причина: `<Action> · <автор>` (`ревью · anna.k`) — без глагола: у логина нет рода;
  4. `body` задачи (у упоминаний — текст заметки) в markdown (HTML → markdown, как в комментариях), не длиннее 6 строк, обрезка `…`; пустой — не показывается.
- **Действия:**
  - `enter`: MR — MR detail этого MR (проект из задачи); issue — экран issue (3.15); прочие типы (коммит, epic, alert, design) — `target_url` в браузере. Открытие цели задачу не закрывает (как в вебе);
  - `x` — отметить выполненной (`POST /todos/:id/mark_as_done`), без confirm: строка сразу убирается из списка pending, счётчик в шапке уменьшается, тост «Готово: !479»; ошибка — строка возвращается на место, тост ошибки. В state done `x` скрыт;
  - `X` — confirm «Отметить все задачи выполненными?», описание «12 задач в To-Do. Вернуть их в TUI нельзя.», по умолчанию «Отмена» → `POST /todos/mark_as_done` → тост «To-Do очищен», перезагрузка, счётчик 0. В state done скрыт;
  - `o` — `<хост>/dashboard/todos` с фильтрами (`state=done`, `type=MergeRequest|Issue`; умолчания не пишутся), `O` — `target_url` выделенной задачи, `y` — копировать её.
- **Пусто:** pending — «В To-Do пусто»; done — «Нет выполненных задач»; с типом — «Нет задач по фильтрам · backspace — сбросить».
- **Поллинг:** 30 с на вершине стека; `r` — мимо кэша.
- **Счётчик в шапке** (3.0): `GET /todos?state=pending&per_page=1` → `X-Total`. Запрашивает корень, а не экран: после `GET /user` при старте, затем раз в 5 мин (замедление без фокуса, 5.7, к нему не применяется); при офлайне и потере авторизации — не запрашивает. Ответ списка To-Do с `state=pending` без фильтра типа тоже обновляет счётчик (`X-Total`), `x` и `X` меняют его сразу. Без `X-Total` (больше 10 000) — `To-Do 9999+`. Ошибка счётчика — только debug-лог: прежнее значение остаётся.

### 3.18. New MR (T37, [#50](https://github.com/4aykovski/glview/issues/50))

Форма создания MR — экран на стеке (не оверлей: полей много, нужна вся высота). Крошки `platform/route-service › MRs › новый MR`. Пока форма открыта, глобальные хоткеи (`p`, `F`, `T`, `?`, `q`, `r`) не действуют: все клавиши — форме (`InputCapturer`). Макета нет.

- **Открытие:** `n` в табе MRs проекта и в групповом табе MRs workspace (проект строки, 3.3). У архивного проекта `n` скрыт.
- **Поля сверху вниз** (одна колонка, подписи слева выровнены):
  1. **Из ветки** — текст с подсказками веток (`Branches`, `search` через 300 мс, до 5 под полем; `↑/↓` выбор, `enter` подставить). Начальное значение — локальная ветка (`.git/HEAD` папки проекта: в режиме проекта — cwd, в workspace — первая папка проекта), даже если на сервере её нет: тогда строка состояния подсказывает `git push`. Detached HEAD, проект без папки и локальная ветка, совпадающая с default-веткой, — пусто.
  2. **В ветку** — так же; начальное значение — default-ветка проекта.
  3. Под ветками — строка состояния (через 300 мс после смены любой ветки; ответы для прежних веток выбрасываются). Порядок запросов: сначала `Branches` (есть ли «из ветки» на сервере); только если ветка есть (или ответ не получен из-за сетевой ошибки), параллельно `Compare` и поиск открытого MR. Если ветки на сервере нет — только «сначала git push», `Compare` и поиск MR не запускаются:
     - `3 коммита · 5 файлов` — `Compare(from=<в ветку>, to=<из ветки>)`; `◐ сравниваем…` пока идёт; ошибка (в том числе сетевая) — «ветка не найдена или сравнение недоступно», не «сначала git push»: «нет на сервере» говорится только когда сервер ответил и ветки в ответе нет;
     - ноль коммитов — Warning «нет изменений: feat/surge не опережает main»;
     - ветки нет на сервере, а локально она есть — Warning «ветки feat/surge нет на сервере — сначала git push» (TUI не пушит, раздел 1);
     - у локальной ветки есть незапушенные коммиты (↑ из `localgit.Tracker`, если известен; git отдельно не запускается) — Muted «2 коммита не запушены — в MR их не будет»;
     - открытый MR из этой пары веток уже есть (`MergeRequests().List` с `State: opened`, `SourceBranch`, `TargetBranch`: GitLab запрещает именно пару, MR из той же ветки в другую целевую дублем не считается) — Warning «из feat/surge уже открыт !482»;
     - запрос открытого MR не удался — Warning «не удалось проверить, есть ли открытый MR из этой ветки»; создание при этом разрешено, а дубль, если он есть, отклонит GitLab (409, сообщение — тостом).
  4. **Заголовок** — текст. По умолчанию — заголовок единственного коммита сравнения, иначе имя ветки по правилу веба GitLab: `-` и `_` → пробел, первая буква заглавная (`feat/surge-pricing` → `Feat/surge pricing`). Следует за ветками, пока его не правили.
  5. **`[ ] Draft`** — флажок (`space`). При создании, если включён, а заголовок не начинается с `Draft:` (без учёта регистра; также `[Draft]`, `(Draft)`), к нему добавляется `Draft: `.
  6. **Шаблон** — выбор из шаблонов описания проекта (`GET /projects/:id/templates/merge_requests`: имена; `↑/↓` и `enter` — список под полем) и «без шаблона». При открытии формы шаблон `Default` (без учёта регистра), если он есть, выбирается и подставляется в пустое описание. Выбор шаблона: описание пустое или не правилось после прошлой подстановки — заменяется содержимым шаблона (`GET …/templates/merge_requests/:name`); иначе confirm «Заменить описание шаблоном «Bug»?», по умолчанию «Отмена». «без шаблона» описание не трогает. Ошибка списка — поле показывает «шаблоны недоступны», форма работает.
  7. **Описание** — многострочное поле (markdown как есть), высота от 3 строк до трети экрана. `enter` — перенос строки, `tab` — следующее поле.
  8. **Assignees**, 9. **Reviewers** — список: выбранные чипами (`@egor ✕ anna.k ✕`), за ними поле поиска. Подсказки — участники проекта (`Members`, `search` через 300 мс, до 5), первой строкой `@me` (текущий пользователь). `enter` добавляет подсказку, уже выбранные в подсказках не показываются, `backspace` в пустом поле убирает последний чип. По умолчанию пусто.
  10. **Labels** — так же, подсказки — `Labels` проекта.
  11. **Milestone** — одно значение с подсказками активных milestones проекта (`Milestones`); пусто — без milestone; `backspace` в пустом поле снимает выбранный.
  12. **Флажки:** `[x] удалить ветку после merge` — по умолчанию `remove_source_branch_after_merge` проекта; `[ ] squash` — по `squash_option`: `default_on` — включён, `default_off` — выключен, `always` — включён и не меняется, `never` — выключен и не меняется (подпись «по настройке проекта»).
  13. **Предпросмотр** (Muted): `будет создан: feat/surge → main · draft · assignee egor · reviewers 2 · labels 1 · milestone 2026-Q4` (пустые части не пишутся).
  14. Низ — `esc закрыть` и кнопка `enter Создать` (как Run pipeline, 3.9).
- **Фокус:** `tab`/`shift+tab` по кругу по полям, флажкам и кнопке. В текстовом поле с видимыми подсказками `enter` подставляет подсказку, без них — следующее поле (в описании — перенос строки). Форма выше экрана прокручивается: поле в фокусе и его подсказки всегда видны. Минимальный размер — 80×24.
- **Проверки перед созданием** (`enter` на кнопке запоминает снимок полей; дальше работа идёт с ним):
  - пустая ветка — «укажи ветку»; ветки совпадают — «ветки совпадают»; пустой заголовок — «укажи заголовок». Ошибка — строкой над кнопкой, фокус в поле с ошибкой;
  - строка состояния веток (п. 3) для снимка ещё не пришла — форма ждёт её («проверяем ветки…», `esc` прерывает ожидание);
  - ветки нет на сервере или ноль коммитов — ошибка строкой над кнопкой, создания нет;
  - открытый MR из этой пары веток есть — confirm «Из feat/surge уже открыт !482 «Fix slot race». Открыть его?», по умолчанию «Да»: «Да» — форма закрывается, открывается MR detail !482; «Отмена» — назад в форму.
- **Создание:** `POST /projects/:id/merge_requests` (5.2). Пока идёт — форма заблокирована, «создаём…», `esc` не действует. Успех — тост «MR !483 создан», сбрасываются кэши списков MR проекта (и групп workspace), форма заменяется экраном MR detail нового MR (`esc` — туда, откуда открыли форму). Ошибка — тост (у 400/409/422 — сообщение GitLab), форма остаётся с теми же значениями.
- **Черновик:** `esc` закрывает форму, значения хранятся в памяти до конца сессии (ключ — хост и проект); повторный `n` в том же проекте восстанавливает их (ветки и заголовок — как были, проверки перезапускаются). Успешное создание черновик стирает. На диск не пишется.
- **Ответы закрытой формы** выбрасываются (`common.Gen`, 6.4).
- **Позже:** MR из форка в upstream (`target_project_id`) и флажок `allow_collaboration` — [#56](https://github.com/4aykovski/glview/issues/56).

## 4. Модель данных

Пакет `internal/gitlab`. Типы — свои, не из client-go. UI видит только их.

```go
type ProjectRef struct {
    ID       int64  // 0, если ещё не известен
    FullPath string // "platform/route-service"
}

type Project struct {
    ProjectRef
    Name           string
    WebURL         string
    DefaultBranch  string
    LastActivityAt time.Time
    Archived       bool
    Starred        bool
    // Только из Projects().Get (REST), для формы New MR (3.18):
    RemoveSourceBranchAfterMerge bool   // remove_source_branch_after_merge
    SquashOption                 string // squash_option: never | always | default_on | default_off; "" — неизвестно
}

type User struct {
    ID       int64
    Username string
    Name     string
    WebURL   string
}

type MergeRequest struct {
    Project        ProjectRef
    IID            int64
    Title          string
    Description    string // markdown, только в деталях
    State          MRState // opened | merged | closed | locked
    Draft          bool
    Author         User
    Assignees      []User
    Reviewers      []User
    SourceBranch   string
    TargetBranch   string
    SHA            string
    Labels         []string
    MergeStatus    string // detailed_merge_status как есть
    HasConflicts   bool
    HeadPipeline   *PipelineSummary
    Approvals      Approvals
    Discussions    DiscussionStats
    Diff           *DiffStats // additions, deletions, files; может отсутствовать
    CommitCount    int        // только в деталях (commitCount); 0 — неизвестно
    TitleLinks       []Link   // только в деталях: <a href> из titleHtml (3.5, «Ссылки MR»)
    DescriptionLinks []Link   // только в деталях: <a href> из descriptionHtml
    WebURL         string
    CreatedAt      time.Time
    UpdatedAt      time.Time
    MergedAt       time.Time // только в деталях; нулевое, если не смержен
    ClosedAt       time.Time // только в деталях; нулевое, если не закрыт
    MergedBy       *User     // только в деталях (mergeUser); может отсутствовать
    RebaseInProgress bool
    MergeError     string // причина неудачного rebase/merge (merge_error)
    Squash         bool   // умолчание squash в диалоге merge
    ForceRemoveSourceBranch bool // умолчание «удалить ветку» в диалоге merge
    DiffRefs       *DiffRefs // только в деталях (diffRefs): SHA для комментариев к строкам; nil — неизвестно
}

type DiffRefs struct{ BaseSHA, StartSHA, HeadSHA string }

// Файл диффа MR (REST /merge_requests/:iid/diffs).
type DiffFile struct {
    OldPath, NewPath string
    NewFile, RenamedFile, DeletedFile bool
    Generated bool   // generated_file; false, если поля нет
    TooLarge  bool   // too_large или collapsed: дифф скрыт сервером
```

## 5. Интеграция с GitLab

### 5.1. Транспорт

- **REST:** `gitlab.com/gitlab-org/api/client-go` (последняя мажорная версия на момент M0). Используется только внутри `internal/gitlab/rest`.
- **GraphQL:** собственный тонкий клиент на `net/http`, `POST {host}/api/graphql`. Обоснование:
  - workspace-запросы динамические: число алиасов `p0…pN` зависит от числа проектов в пачке, а genqlient генерирует только статические запросы под фиксированную схему;
  - genqlient требует выгружать схему GitLab, а она различается между версиями self-hosted инстансов;
  - нужно мало: `Do(ctx, query, vars, out)`, разбор `errors`, распознавание ошибки сложности. Это около 200 строк;
  - типобезопасность компенсируем: запросы лежат константами рядом с типами ответа, на каждый есть тест с JSON-фикстурой.
- **Общий `http.Client`:** таймаут запроса 15 с, свой `ca_file` и `insecure_skip_verify` из конфига, заголовок `PRIVATE-TOKEN` (REST) и `Authorization: Bearer` (GraphQL), `User-Agent: gitlab-tui/<ver>`.
- **Ограничение параллелизма:** глобальный семафор на 6 одновременных запросов на хост.
- **429:** уважаем `Retry-After`, ждём (не дольше 30 с), затем один повтор и тост «GitLab ограничил запросы».
- **Версия инстанса:** `GET /version` при старте, кэш на сессию. Используется для фич с разной поддержкой (auto-merge, раздел 5.5).

### 5.3. GraphQL-батчинг

Запрос workspace собирается из фрагмента и списка проектов:

```graphql
query WsMRs($me: String!, $first: Int!, $p0: ID!, $p1: ID!, …) {
  p0: project(fullPath: $p0) { ...WsMRGroup }
  p1: project(fullPath: $p1) { ...WsMRGroup }
}
fragment WsMRGroup on Project {
  fullPath
  mergeRequests(state: opened, first: $first, sort: UPDATED_DESC) {
    count
    nodes { ...MRRow }
  }
}
```

**Правила:**

- Пути проектов передаются переменными, не вставляются в текст запроса. Фрагменты держат текст запроса под лимитом 10 000 символов.
- `project: null` в ответе → `ProjectGroup.Err = ErrNotFound`, у группы пометка «нет доступа». Остальные группы не страдают.
- Частичные `errors` с `path`, указывающим на `pK`, привязываются к своей группе. Если `pK` при этом пришёл не `null`, разобранные поля группы используются: ошибка поля (например, нет доступа к CI в `pipelines`) пишется в debug-лог и не выбрасывает строку; поле без данных остаётся пустым.

**Лимит сложности** (250 для авторизованных, [docs](https://docs.gitlab.com/api/graphql/)):

1. Стартовый размер пачки — `graphql.batch_size` (по умолчанию 10).
2. На ошибку «Query has complexity of X, which exceeds max complexity of 250» новый размер = `floor(size × 250 / X × 0.9)`, минимум 1. Пачка делится, запрос повторяется.
3. Выученный размер запоминается на сессию для каждого вида запроса (MRs, MRs+«я», Pipelines, Projects).
4. Если инстанс поддерживает поле `queryComplexity { score limit }`, первый запрос запрашивает его и калибрует размер заранее.

**Поток:**

- Пачки идут параллельно, не больше 3 одновременно, каждая — отдельный `tea.Cmd`.
- Каждая пачка возвращает `WsBatchMsg{Gen, Tab, Groups []ProjectGroup[T]}`. Экран вклеивает группы по мере прихода.
- Порядок групп на экране — по `lastActivityAt` из фазы 1 (или кэша), а не по порядку ответов, чтобы строки не прыгали.

**Таймаут:** у пачки свой, 30 с (как у GraphQL на сервере). По таймауту пачка делится пополам и повторяется один раз.

### 5.4. Пагинация

- **GraphQL:** курсоры `pageInfo{hasNextPage endCursor}`, `first: 20`.
- **REST:** offset-пагинация `page`/`per_page=20` по заголовкам `X-Next-Page`/`X-Total`. Если `X-Total` нет (больше 10 000 записей), счётчик показывается как `20 из многих`. Keyset не используем: эндпоинты экранов его не поддерживают.
- **Подгрузка:** курсор в пределах 5 строк от конца загруженного → запрос следующей страницы. В конце списка строка `◐ загружаю ещё…`, по ошибке — `✗ не удалось загрузить, r — повторить`.
- **Workspace:** без пагинации внутри групп. «Ещё N» ведёт в режим проекта.

### 5.5. Совместимость версий

- **Минимальная поддерживаемая версия GitLab — 16.0.** Ниже — предупреждение в тосте при старте, без блокировки.
- **Auto-merge:** на GitLab ≥ 17.11 — `auto_merge=true`, ниже — `merge_when_pipeline_succeeds=true` (в 17.11 его объявили deprecated).
- **Approvals:** `approvalsRequired`/`approvalsLeft` на CE обычно 0. Колонка Appr тогда показывает число апрувов без знаменателя (`2`, а не `2/2`).
- **Неизвестное поле GraphQL** на старом инстансе: ошибка `Field 'x' doesn't exist` логируется. Для опциональных полей (`diffStatsSummary`, `queryComplexity`) есть запасной запрос без них, решение кэшируется на сессию.

### 5.6. Лог джобы: поллинг и разбор

**Хвост:**

- `GET /jobs/:id/trace` возвращает весь лог. Храним прочитанную длину в байтах. Новый ответ длиннее — разбираем только хвост с учётом незавершённой последней строки. Короче (ретрай, обрезка) — полный перезапуск разбора.
- Пока джоба running или pending — запрос каждые 3 с, параллельно `GET /jobs/:id` для статуса. После финального статуса — последний запрос лога и остановка.
- Внутренний инкрементальный эндпоинт веб-интерфейса (`/-/jobs/:id/trace.json`) не используем: он не является публичным API. Это возможная оптимизация после MVP.

**Разбор строк:**

- Секции:
  - начало — `section_start:<unix>:<name>[<opts>]\r\x1b[0K<заголовок>`, опция `collapsed=true` учитывается;
  - конец — `section_end:<unix>:<name>\r\x1b[0K`;
  - секции вкладываются; длительность = end − start.
- `\r` внутри строки (прогресс-бары): от строки остаётся текст после последнего `\r`, кроме служебных `\r` маркеров секций.
- Escape-последовательности: SGR (`\x1b[…m`) сохраняются, остальные CSI/OSC (`\x1b[0K`, перемещения курсора) вырезаются.
- Ширина строк считается по видимым символам (`ansi.StringWidth`).

**Память:**

- Модель хранит строки, разобранные в структуры `{Text (с SGR), Plain (без SGR, для поиска), Section}`.
- Логи больше 50 000 строк: в памяти держим последние 50 000 и строку «… начало обрезано, o — открыть полный лог в браузере».

### 5.7. Поллинг и обновление

- **Только у экрана на вершине стека.** Экран получает `ActivatedMsg` и `DeactivatedMsg` при изменениях стека. На Deactivated он увеличивает `pollGen`, и уже запланированные тики со старым gen игнорируются.
- **Адаптивный интервал:**

| Состояние | Интервал |
|---|---|
| Есть running/pending пайплайны или джобы на экране, rebase в процессе | 3 с |
| Списки режима проекта, детали | 30 с |
| Счётчик To-Do в шапке (корень, не экран) | 5 мин (3.17) |
| Workspace (табы MRs/Pipelines/Tags/Проекты) | 60 с; в MRs/Pipelines — только раскрытые группы и обзор для заголовков свёрнутых; в Pipelines при running/pending — дополнительно 3 с, но только по раскрытым проектам с такими пайплайнами |
| Терминал не в фокусе (`tea.BlurMsg`, если терминал сообщает о фокусе) | ×5, но не реже 5 мин |

- **`r`** — немедленное обновление со сбросом кэша для экрана. В шапке `⟳ 14s` — время с последнего успешного обновления.
- **После действия** (approve, retry…) — сразу перезапрос объекта, не дожидаясь тика.

### 5.8. Кэш

Пакет `internal/cache`, в памяти. Ключ — каноническая сигнатура запроса.

- **TTL:**

| Данные | TTL |
|---|---|
| `GET /user`, `/version` | сессия |
| `rootRef` и метаданные проекта | 24 ч |
| Списки | 30 с |
| Финальные пайплайны и джобы | 10 мин |
| Дифф MR (ключ с head SHA) | 10 мин |
| Шаблоны описания MR (список и содержимое) | 5 мин |
| Счётчик To-Do | не кэшируется: запрашивает только корень (3.17) |
| Последний тег проекта workspace | 10 мин (только для тиков поллинга; `r` перезапрашивает) |
| Running | 0 (не кэшируются) |

- **Stale-while-revalidate:** устаревшее значение отдаётся сразу (`Stale: true`), фоновый запрос обновляет его, экран перерисовывается по приходу.
- **На диске** (`$XDG_CACHE_HOME/gitlab-tui/`): только starred (`starred/<sha256(хост)[:16]>.json`, 1 ч, свой файл на хост) и метаданные проектов workspace (для мгновенного старта): `workspace/<sha256(хост + "\n" + источник)[:16]>.json` — список `ProjectOverview` без MR, со статусом пайплайна default-ветки, `rootRef` и временем снимка; без токенов. Недавние проекты — в `$XDG_STATE_HOME/gitlab-tui/state.json`, отдельный список на хост (последние 20 на хост); старое поле `recent` без хоста игнорируется и удаляется при следующей записи.
- **Раскрытые группы workspace** — там же, в `state.json`: `hosts.<хост>.workspaces.<источник>` = `{"at": <время последнего открытия>, "expanded": {"mrs": [пути проектов], "pipelines": [...], "tags": [...]}, "selected": {"mrs": [пути проектов], "pipelines": [...], "tags": [...]}}` (`selected` — отмеченные в `P`); источник — тот же, что в ключе снимка workspace (папка или группа). На хост хранится не больше 50 workspace, при переполнении выбрасываются давно не открывавшиеся. Нет записи — все группы свёрнуты. Повреждённый файл — пустое состояние, как для недавних.
- **Инвалидация:** любое действие сбрасывает ключи этого объекта и его списков.

**Почему Bubble Tea v2:**

1. **Это стабильная ветка.** v2.0.0 вышла как мажорный релиз, сейчас актуальна v2.1.0 ([releases](https://github.com/charmbracelet/bubbletea/releases)) после серии патчей v2.0.x.
2. **Экосистема уже на v2.** Huh v2 «built on the all-new Bubble Tea v2 and Lip Gloss v2» ([huh releases](https://github.com/charmbracelet/huh/releases)), Glamour v2 использует Lip Gloss v2 ([glamour releases](https://github.com/charmbracelet/glamour/releases)). Смешивать v1 и v2 нельзя, а новый код на v1 сразу стал бы legacy.
3. **glab на v2.** Сам glab обновляется на `charm.land/bubbletea/v2` ([пример MR](https://gitlab.com/gitlab-org/cli/-/merge_requests/3793)), то есть ветка проверена на похожем приложении.
4. **Нужные возможности есть только в v2:**
   - события фокуса терминала (`FocusMsg`/`BlurMsg`) — для замедления поллинга;
   - запрос цвета фона (`RequestBackgroundColor` → `BackgroundColorMsg`) — для выбора светлого или тёмного варианта темы;
   - OSC52-буфер обмена (`SetClipboard`) — для `y`;
   - улучшенная обработка клавиш (различение `shift+…`, `ctrl+…` в поддерживающих терминалах);
   - декларативный `View` без глобального рендерера Lip Gloss.

Следствие: в Lip Gloss v2 `lipgloss.Color(...)` возвращает `color.Color` (`image/color`), а не отдельный тип. Поэтому поля `Theme` — `color.Color` (раздел 9).

### 6.4. Асинхронность

- **Каждый запрос — `tea.Cmd`** с `context.WithTimeout`. Экран хранит `cancel` текущих запросов и отменяет их при pop или новом запросе того же вида.
- **Generation counter.** У экрана `gen uint64`, он увеличивается при смене фильтра, таба или при `r`. Команда захватывает текущий gen. В `Update` msg с `Gen != m.gen` выбрасывается. Так ответ на старый фильтр не перетрёт новый.
- **Тики поллинга** — отдельный `pollGen` (раздел 5.7).
- **Мутации** (approve, merge…) не используют gen экрана. Они всегда показывают тост с результатом и инициируют перезапрос.
- **Корневая модель:**
  - раздаёт `tea.WindowSizeMsg` всем экранам стека;
  - `LangChangedMsg` и `ThemeChangedMsg` — тоже всем, чтобы нижние экраны были готовы к возврату;
  - остальные msg — только вершине (и оверлею, если он открыт).

## 7. Конфиг

**Путь:** `$XDG_CONFIG_HOME/gitlab-tui/config.yaml`, по умолчанию `~/.config/gitlab-tui/config.yaml` на всех ОС, включая macOS. `os.UserConfigDir` не используем, он дал бы `~/Library/Application Support`.

- **Права:** файл пишется с правами `0600`. Если в нём есть токен, а права шире, при старте показывается тост-предупреждение.
- **Ошибка разбора YAML:** запуск не прерывается. Тост с номером строки, используются значения по умолчанию.
- **Неизвестное значение перечисления** (например, `run_pipeline.refs_first: foo`, `theme: foo`): используется значение по умолчанию, тост-предупреждение с ключом.
- **Запись:** только то, что меняет TUI (`language`, `host`/`token` из Setup). Запись сохраняет порядок ключей и комментарии: через `yaml.Node`.

```yaml

tls:
  ca_file: ""                        # свой CA для self-hosted

  max_group_projects: 100            # лимит проектов для workspace из группы

project:
  page_size: 20

run_pipeline:                        # форма Run pipeline (3.9)
  refs_first: branches               # branches | tags — какая группа первой в подсказках ref
  prefill_local_branch: true         # подставить текущую локальную ветку и поставить её первой

graphql:
  batch_size: 10                     # стартовый размер пачки, дальше адаптивно

  - pattern: '[A-Z][A-Z0-9]+-\d+'     # регулярное выражение Go (RE2)

# custom_commands:
```

**Правила `links`:** для трекеров без интеграции в GitLab (с интеграцией ссылки уже приходят в `titleHtml`/`descriptionHtml`). `url` — шаблон `regexp.Expand`. Правило с пустым `pattern` или `url`, с ошибкой в регулярке или с `url`, который не начинается с `http://` или `https://`, пропускается с тостом-предупреждением с ключом (`links[0].pattern`); остальные правила работают. По умолчанию правил нет.

**Цепочка источников:**

- **Хост:** флаг URL в `-p` → `config.host` → env `GITLAB_HOST` → хост remote → Setup.
- **Токен:** `config.token` → env `GITLAB_TOKEN` → glab для этого хоста → Setup.
- В Help показывается, откуда взят токен: config / env / glab. Сам токен нигде не печатается.

## 8. i18n

Пакет `internal/i18n`, без внешних библиотек.

```go
type Lang string

    EN Lang = "en"
    RU Lang = "ru"

type Messages struct {
    Tabs struct {
        Projects, MRs, Pipelines, Issues, Tags string
    }
    Filters struct {
        Me, NotApplicableToTags, Project, State string

    }

    }

    }
    Plural struct {
        MoreN        func(n int) string // «ещё 3» / «3 more»
        Projects     func(n int) string // «5 GitLab-проектов»

    }
    RelTime RelTimeFormats
}

type PluralForms struct{ One, Few, Many string } // для en Few == Many

func Get(l Lang) *Messages
func Plural(l Lang, n int, f PluralForms) string
func RelTimeShort(l Lang, d time.Duration) string // en: 4m 1h 2d 3w 1mo 1y; ru: 4м 1ч 2д 3н 1мес 1г
func RelTimeLong(l Lang, d time.Duration) string  // «4 минуты назад» / «4 minutes ago»
```

**Плюрализация:**

- Русское правило: `n%10==1 && n%100!=11` → one; `n%10 in 2..4 && n%100 not in 12..14` → few; иначе many.
- Английское: `n==1` → one, иначе many.

**Строки:**

- Сообщения — Go-литералы структур (`en.go`, `ru.go`), поэтому опечатка в имени поля не скомпилируется.
- Тест через reflection проверяет, что все строковые поля и функции заполнены в обоих языках.

**Переключение:**

- `ctrl+l` переключает RU↔EN. Корень сохраняет `language` в конфиг и рассылает `LangChangedMsg`.
- Экраны и компоненты пересобирают keymap и help, заголовки колонок, плейсхолдеры `textinput`, тексты `help.Model`.
- Открытая форма huh пересобирается: значения лежат в привязанных переменных и не теряются, `huh.KeyMap` получает переведённые `Help`.
- Автоопределения по `LANG` нет: пустое значение → `en`.

**Что переводим и что нет:**

- Переводим: табы, фильтры, заголовки колонок, подсказки, тосты, ошибки, относительное время, пустые состояния.
- Не переводим: данные GitLab (заголовки, имена, ветки, описание), статусы пайплайнов и джоб (`running`, `failed`), `detailed_merge_status`. Рядом со статусом может стоять переведённая подпись.

**Ширина:**

- Всегда `lipgloss.Width`: русские строки длиннее английских.
- Футер собирается из `Short()` по убыванию `Priority`, пока влезает в ширину минус правый блок. `?` всегда остаётся.

## 9. Темы

### 9.1. Семантические роли

Экраны не знают цветов. Они используют только `Styles`, построенные из `Theme`.

```go

import "image/color"

type Theme struct {
    Name      string
    Fg        color.Color // основной текст
    Muted     color.Color // второстепенный текст, заголовки колонок
    Border    color.Color
    Accent    color.Color // имя приложения, хоткеи, активный таб, IID выбранной строки
    Selection color.Color // фон выбранной строки; nil → reverse
    Warning   color.Color // ⚠ conflicts, предупреждения

type Styles struct {
    App, Header, HeaderMuted, Breadcrumb lipgloss.Style

    ColumnHeader, Row, RowSelected, RowMuted lipgloss.Style
    GroupHeader, GroupHeaderCollapsed, MoreRow lipgloss.Style
    Preview, PreviewTitle                lipgloss.Style

    Toast map[ToastLevel]lipgloss.Style
```

### 9.2. Тема `terminal`

Только 16 ANSI-цветов, `lipgloss.Color("0")…("15")`. Реальные значения задаёт тема терминала пользователя.

| Роль | Тёмный фон | Светлый фон |
|---|---|---|
| Fg | `NoColor` (цвет терминала по умолчанию) | `NoColor` |
| Muted | `8` | `8` |
| Border | `8` | `8` |
| Accent | `3` (yellow) | `4` (blue) |
| Selection | `nil` → reverse | `nil` → reverse |
| Warning | `3` | `1` |
| Success | `2` | `2` |
| Failed | `1` | `1` |
| Running | `4` | `4` |
| Pending | `3` | `3` |
| Manual | `5` | `5` |
| Canceled | `8` | `8` |
| Diff Add / Del | `2` / `1` | `2` / `1` |

- **Выделение строки** — `Reverse(true)`, без цвета фона. Работает на любой теме и без цвета. IID выбранной строки — Accent + Bold, маркер `›`.
- **Активный таб** — `Reverse + Bold` поверх Accent: фон акцента, текст цвета фона, как в макете.
- **Светлый или тёмный фон:**
  - при старте отправляется `tea.RequestBackgroundColor`; по `BackgroundColorMsg` собирается `TerminalTheme(isDark)` и рассылается `ThemeChangedMsg`;
  - до ответа (и если терминал не отвечает) считаем фон тёмным;
  - Accent меняется, потому что жёлтый на светлом фоне в большинстве терминальных тем нечитаем.
- **Статусы** отличаются и цветом, и глифом (раздел 4), так что ни одна роль не держится на цвете в одиночку.
- **Markdown:**
  - glamour получает `ansi.StyleConfig`, собранный из `Theme`: заголовки — Accent + Bold, код — Muted, ссылки — Running, цитаты — Muted;
  - встроенные стили glamour `dark`/`light` не берём: они используют 256 цветов;
  - подсветка блоков кода — chroma с форматтером `terminal16`.
- **Диффы (после MVP):** chroma `terminal16`, плюс фон и цвет строк из `Diff.Add`/`Diff.Del`.

**`NO_COLOR`:**

- Lip Gloss v2 через `colorprofile` при `NO_COLOR` переходит на профиль Ascii и выбрасывает все цвета. Bold и reverse остаются: выделение и активный таб видны, статусы различимы по глифам.
- glamour в этом режиме получает стиль `notty`.

**Тема `terminal-faint`** (`theme: terminal-faint`, по умолчанию остаётся `terminal`): Muted в ANSI 8 в Solarized Dark совпадает с фоном (base03), поэтому здесь второстепенный текст (Muted, заголовки колонок, описания клавиш, статусы created/skipped/canceled) рисуется цветом терминала по умолчанию с атрибутом Faint, без ANSI 8. Border на тёмном фоне — ANSI `0` (в Solarized это base02, отличим от фона), на светлом — как в `terminal`. В markdown код и цитаты — Faint вместо Muted. Faint — атрибут, как Bold и reverse, поэтому при `NO_COLOR` он остаётся. Faint рисуется не везде одинаково (часть терминалов показывает его как обычный цвет или слишком тускло), поэтому тема включается по выбору. Неизвестное значение `theme` — тост-предупреждение и `terminal`.

### 9.3. Точка расширения под кастомные темы

- `common.Theme` уже отделена от `Styles`. Новая тема — это только новый конструктор `Theme`.
- Реестр тем (после MVP):

```go
type ThemeProvider interface {
    Name() string
    Theme(isDark bool) Theme
}

// Встроенные: terminal, terminal-faint (MVP), catppuccin, gruvbox… (после MVP);
// файлы ~/.config/gitlab-tui/themes/*.toml → TOMLTheme (после MVP).
```

- Смена темы на лету идёт тем же путём, что и смена языка: `ThemeChangedMsg` → корень пересобирает `Styles` → рассылает всем экранам. Экраны хранят `*Styles`, а не отдельные стили, поэтому новая тема применяется одной заменой указателя.
- **Правило код-ревью:** в `ui/screens` запрещены `lipgloss.Color(...)` и `lipgloss.NewStyle().Foreground(...)`. Проверка — простой тест-грепом в CI.

## 10. Внешние инструменты: glab и git

glab — опциональная зависимость. Как Go-библиотеку не используем: почти весь код glab лежит в `internal/`. Его вывод вместо API не парсим.

### 10.1. Обнаружение

- При старте: `glab.enabled != false` → `exec.LookPath(config.glab.path || "glab")` → `Glab{Path}` или `nil`.
- `glab == nil` → все glab-действия получают `Hidden: true`: их нет ни в футере, ни в хелпе. В Help строка «glab не найден — checkout недоступен».
- **Проверка входа на хост** — лениво, при первом glab-действии или при открытии Help: `glab auth status --hostname <host>`, по коду возврата. Не 0 → тост «glab не залогинен на <host>: выполни `glab auth login --hostname <host>`», действие не запускается.
- Все вызовы glab для проверок — с таймаутом 3 с и без stdin.

### 10.2. Токен из glab

Это третий шаг цепочки после config и `GITLAB_TOKEN`.

1. `glab config get token --host <host>` → stdout без пробелов. Непусто → берём.
2. Пусто (токен в keyring) → `glab auth status --hostname <host> --show-token --output json` → поле токена из JSON. Флаги `--show-token` и `--output json` есть в [документации](https://docs.gitlab.com/cli/auth/status/).
3. Ошибка или пусто → дальше по цепочке, то есть Setup.

Полученный токен проверяется обычным `GET /user`. Он не сохраняется в конфиг и не логируется.

Риск: в glab ≥ 1.84 есть открытый баг с токенами из keyring ([cli#8168](https://gitlab.com/gitlab-org/cli/-/work_items/8168)). Поэтому оба пути проверяем на живом glab в задаче M0, а точное имя JSON-поля фиксируем в тесте с записанным выводом.

### 10.3. Exec-действия

Встроенные glab-действия описываются той же структурой, что будущие custom commands:

```go
// internal/glab

type Context string // mr | pipeline | job | tag | issue | project

type Action struct {
    ID       string   // "mr.checkout"
    Key      string   // "C"
    Context  Context
    Command  string   // text/template: "glab mr checkout {{.MR.IID}}"
    NeedsRepo bool    // нужна локальная папка проекта (cmd.Dir)
    NeedsGlab bool
    Refresh  []RefreshKind // что перечитать после выхода: Branch, MR, ...
}

type TemplateData struct {
    Host    string
    Project gitlab.Project
    MR      *gitlab.MergeRequest
    Pipeline *gitlab.PipelineSummary
    Job     *gitlab.Job
    Tag     *gitlab.Tag
    Issue   *gitlab.Issue
}

func (a Action) Cmd(d TemplateData, repoDir string) (*exec.Cmd, error)
func BuiltinActions() []Action
```

**Checkout МРа (MVP):**

- `C` на MR в списке MR проекта или в MR detail.
- Доступно, если glab найден и у проекта есть локальная папка: режим проекта из cwd, проект workspace из LocalDirSource или проект, открытый через `-p`/`p`/`F`, путь которого совпал с одной из известных локальных папок. Иначе действие скрыто.
- `tea.ExecProcess(exec.Command(glab, "mr", "checkout", iid))` с `cmd.Dir = repo.Root`. TUI отдаёт терминал glab'у, по завершении возвращается.
- По `ExecFinishedMsg`: перечитываем `.git/HEAD` → обновляются шапка и колонка «Локальная ветка», превью показывает «локально на <branch> → !iid». Код возврата не 0 → тост «glab завершился с ошибкой (код N)», вывод glab пользователь видел в терминале.
- Подтверждения нет: действие локальное и обратимое (ветку можно сменить обратно). Если в рабочей копии есть изменения, glab сам откажется или спросит.

### 10.4. Локальный git: fetch и pull

git — опциональная зависимость, как glab. При старте выполняется `exec.LookPath("git")`; нет git → `u`/`U` скрыты, колонка ↑↓ пустая.

**Системный git, не go-git.** go-git не учитывает настройки пользователя: credential helpers, `core.sshCommand`, `url.insteadOf`, `includeIf`. Системный git применяет их как есть.

**Действия:**

| Клавиша | Где | Что делает | Подтверждение |
|---|---|---|---|
| `u` | workspace, любой таб | `git fetch --prune <remote>` во всех локальных репозиториях workspace: GitLab и серых не-GitLab | нет: меняются только remote-ссылки, рабочие копии не трогаются |
| `U` | workspace, любой таб | fetch, затем `git merge --ff-only @{u}` в тех же репозиториях | confirm со списком: «обновить 11 репозиториев, пропустить 2 (detached, нет upstream)» |
| `u` / `U` | режим проекта с локальной папкой | то же для одного репозитория | `U` — confirm |

- Workspace из группы (`GroupSource`) локальных папок не имеет, `u`/`U` там скрыты.
- `<remote>` — remote, по которому определён проект (обычно `origin`). Если upstream текущей ветки (`branch.<name>.remote`) — другой remote, он скачивается тоже (`git fetch --prune <upstream-remote>`), иначе ↑↓ и `merge --ff-only @{u}` работали бы по устаревшим ссылкам. Upstream `.` (локальная ветка) отдельно не скачивается.

**Почему pull только fast-forward.** `merge --ff-only @{u}` вместо `git pull`:
- не зависит от `pull.rebase` и других настроек pull у пользователя;
- никогда не создаёт merge-коммит и не оставляет репозиторий в состоянии конфликта.

Разошедшаяся ветка или мешающие локальные изменения — это пропуск с причиной, а не ошибка посреди merge.

**Предпроверки перед `U`.** Читаются из файлов, без git. Репозиторий пропускается (`○`) с причиной, если:
- detached HEAD;
- у ветки нет upstream (`branch.<name>.remote`/`merge` в `.git/config`);
- идёт merge или rebase (`MERGE_HEAD`, `rebase-merge/`, `rebase-apply/`).

**Запуск без терминала.** TUI занимает терминал, поэтому git не должен ничего спрашивать:

- `stdin = /dev/null`, `GIT_TERMINAL_PROMPT=0`;
- процесс запускается в новой сессии (`SysProcAttr.Setsid`), без управляющего терминала. ssh и credential helpers не могут открыть `/dev/tty` и перехватить ввод TUI: при нехватке авторизации они быстро падают с ошибкой;
- ssh-agent, Keychain и credential helpers без интерактива работают как обычно;
- таймаут — `git.timeout` (60 с) на репозиторий, параллельно — `git.parallel` (6). Выход из TUI отменяет все процессы через ctx.

**Результаты:**

| Статус | Глиф | Когда |
|---|---|---|
| обновлено | `✓` | fetch прошёл, или pull сдвинул ветку (`✓ +3`) |
| актуально | `✓` muted | pull: уже на upstream |
| пропущено | `○` | предпроверки, ветка разошлась (`○ разошлась`), мешают локальные изменения |
| ошибка | `✗` | авторизация, сеть, таймаут, прочее |

- **stdout и stderr** захватываются, последние 20 строк хранятся для превью строки.
- **Классификация ошибок:** код возврата и несколько известных шаблонов stderr: `Permission denied`, `could not read Username`, `Host key verification failed` → «нужна авторизация»; `Could not resolve host` → «сеть»; `Not possible to fast-forward` / `diverged` → «разошлась»; `would be overwritten` → «мешают локальные изменения». Всё остальное — последняя строка stderr как есть.
- **Данные из вывода git не берём.** ↑↓ считаются отдельной командой.
- **Подсказка** для «нужна авторизация»: «выполни `git fetch` в <папка> вручную (ssh-ключ, known_hosts)».

**Ход операции:**
- в шапке `⟳ fetch 7/13`, у строк таба «Проекты» `◐`;
- итоговый тост «fetch: 12 ✓, 1 ✗ (route-planner-ui: нужна авторизация)»;
- повторный `u` во время операции игнорируется с тостом «fetch уже идёт».

**↑↓ (ahead/behind):**
- команда — `git rev-list --left-right --count HEAD...@{u}`;
- считается после каждого fetch/pull и один раз в фоне при старте workspace (локальная операция, параллельно 8);
- показывается в колонке ↑↓ таба «Проекты» и в шапке режима проекта (`fix/slot-race ↓3`);
- после pull перечитывается `.git/HEAD`.

**`git.fetch_on_start: true`** — фоновый fetch всех репозиториев при открытии workspace. По умолчанию выключен: сетевые операции только по явной команде.

```go
// internal/gitexec

type Op int // OpFetch | OpPullFF

type Status int // StatusUpdated | StatusUpToDate | StatusSkipped | StatusFailed

type Reason string // auth | network | diverged | dirty | timeout | detached | no-upstream | no-remote | in-progress | other

type Result struct {
    Dir           string
    Op            Op
    Status        Status
    Reason        Reason   // причина пропуска или ошибки; UI переводит
    Detail        string   // для other — последняя строка вывода git
    Ahead, Behind int
    HasUpstream   bool     // ↑↓ известны
    Moved         int      // pull: на сколько коммитов сдвинулась ветка
    Output        []string // последние 20 строк stdout и stderr
}

func Precheck(repo gitremote.Repo) Reason // предпроверки pull из файлов

type Runner interface {
    // Результаты приходят по мере готовности репозиториев; канал закрывается в конце.
    Run(ctx context.Context, op Op, repos []gitremote.Repo) <-chan Result
    AheadBehind(ctx context.Context, repo gitremote.Repo) (ahead, behind int, err error) // ErrNoUpstream — пусто
}
```

В UI канал превращается в `localgit.ProgressMsg{Result}` и `localgit.DoneMsg` по тому же паттерну, что батчи GraphQL (6.3). Состояние операций (идёт ли, `done/total`, последний результат и ↑↓ по папкам) хранит `localgit.Tracker` в `app.Env`; корень передаёт ему сообщения и раздаёт их всем экранам стека.

### 10.5. После MVP

Всё ниже ложится на `Action`:

- `glab repo clone <path> <workspace>/<name>` из `F` (`Context: project`, `NeedsRepo: false`), затем пересканирование `LocalDirSource`.
- ~~`glab mr create`~~ — заменён формой New MR (3.18, T37).
- `glab ci lint` перед запуском пайплайна: шаг в Run pipeline, если glab найден.
- `custom_commands` из конфига: те же `Action` с `ID: "custom.N"`. Валидация при загрузке: шаблон компилируется, контекст известен, `key` не конфликтует со встроенными хоткеями этого контекста (конфликт — ошибка загрузки с понятным текстом, а не тихое переопределение).

## 11. Ошибки и пограничные случаи

### 11.1. Ошибки API → сообщения

Слой `gitlab` переводит HTTP и GraphQL ошибки в доменные:

| Ошибка | Признак | Тост | Подсказка |
|---|---|---|---|
| `ErrUnauthorized` | 401 | «Токен не принят» | источник токена: config → «обнови token в config.yaml»; env → «проверь GITLAB_TOKEN»; glab → «выполни `glab auth login --hostname <host>`» |
| `ErrForbidden` | 403 | «Недостаточно прав» | 403 `insufficient_scope` → «у токена нет scope `api` (только чтение)» |
| `ErrNotFound` | 404, `project: null` | «Не найдено или нет доступа» | — |
| `ErrConflict` | 409 | merge: «в ветку запушили, обнови (r)»; rebase: «не удалось поставить rebase в очередь»; прочие действия: «объект изменился, обнови (r)» | — |
| `ErrNotMergeable` | 405, 422 | «Нельзя смержить: <detailed_merge_status>» | — |
| `ErrRateLimited` | 429 | «GitLab ограничил запросы, повтор через N с»: N — `Retry-After`, округлённый вверх; без заголовка 30 | — |
| `ErrNetwork` | DNS, отказ соединения, таймаут | «Хост недоступен» | — |
| `ErrTLS` | сертификат не принят | «Ошибка TLS» | `tls.ca_file` (в хинте тоста) |
| `ErrComplexity` | GraphQL | не показывается пользователю | обрабатывается батчером |

- **Тосты:** живут 4 с (Error — 8 с), не больше одного одновременно, новый вытесняет старый. Тост показывается в правой части футера вместо статусной подсказки экрана и пропадает по истечении срока.
- **401 посреди сессии:** поллинг всех экранов останавливается, в шапке появляется `✗ auth`, `r` проверяет токен заново.
- **Офлайн:**
  - офлайн — это подряд идущие сетевые ошибки (`ErrNetwork`: DNS, отказ соединения, таймаут) любых запросов; любой HTTP-ответ, в том числе 5xx и 429, и ошибка TLS офлайном не считаются. Транспорт сообщает исход каждого запроса монитору доступности (`gitlab.Monitor`), UI читает его;
  - экраны показывают данные из кэша с пометкой в шапке `⟳ 5m (офлайн)`;
  - поллинг продолжается с экспоненциальной задержкой: база × 2ⁿ (n — число подряд неудач), не меньше базы и не больше 60 с (если база сама больше, она не меняется);
  - при восстановлении (первый же ответ) — один тост «соединение восстановлено», задержки возвращаются к базовым.

### 11.2. Пограничные случаи

| Случай | Поведение |
|---|---|
| Пустые списки | Текст пустого состояния с текущими фильтрами: «Нет открытых MR, где ты ревьюер. m — снять фильтр «я»» |
| Workspace без GitLab-проектов | 2.4 |
| Проект workspace удалён или нет доступа | Группа «✗ нет доступа» в табах, в «Проектах» серым; не ломает остальные |
| Две папки с одним проектом | Обе строки в «Проектах», в групповых табах проект один (дедупликация по пути); checkout — в папку текущей строки |
| Архивный проект | Строка с пометкой `archived`, действия записи (merge, tag…) скрыты |
| Пайплайн без стейджей или джоб (ошибка YAML) | Pipeline показывает `yaml_errors` из ответа и статус |
| Bridge без downstream (ещё не создан) | `⇢ <project> · ждёт <stage>`, `enter` недоступен |
| Downstream в проекте без доступа | `⇢ нет доступа`, `enter` → тост |
| Джоба без лога (created, skipped) | Job log с текстом «лог пуст: джоба <status>» |
| Лог очень большой | 5.6 (обрезка начала, `o`) |
| `ciConfigVariables` вернул `null` | Сервер считает конфиг асинхронно: повтор через 1, 2, 4 с, потом «подсказки недоступны» без блокировки формы |
| Нет прав Developer для запуска пайплайна, тега | Действие видно; ответ 403 → тост «недостаточно прав» |
| Protected tag | Удаление → 403 → «тег защищён» |
| Нет semver-тегов | Варианты `v0.0.1`, `v0.1.0`, `v1.0.0`, по умолчанию `v0.1.0`; есть только тег без `v` → сохраняем стиль (`1.2.3` → `1.2.4`). Теги не вида `[v]X.Y.Z[-pre][+build]` (`latest`, `v1.2`) не учитываются |
| Последний тег — prerelease (`v1.14.0-rc2`) | База — последний не-prerelease; релиз `v1.14.0` — вариант по умолчанию: совпал с patch/minor/major — у варианта пометка `release` (`v1.14.0 (minor · release)`), не совпал — отдельный вариант `v1.16.0 (release)` |
| Rebase долго в процессе | Чип `◐ rebase…`, поллинг 2 с до 2 мин, потом тост «rebase ещё идёт» и обычный поллинг |
| Узкий терминал (< 80) | Сообщение «расширь терминал до 80×24», без попытки отрисовать |
| Смена ветки снаружи TUI | `.git/HEAD` перечитывается на каждом обновлении экрана (`r`, тики), дешёвое чтение файла |
| Группа в `F` с > 100 проектов | Берутся 100 самых активных, в шапке «показаны 100 из 342»; без `X-Total` (больше 10 000) — «показаны 100 из многих» |
| Ошибка загрузки списка проектов группы | Тост с ошибкой, в шапке состояние ошибки; `r` повторяет загрузку списка, а не только обзора |
| Дифф файла скрыт GitLab (`too_large`, `collapsed`) | Файл свёрнут с пометкой `слишком большой`, `o` — файл в браузере (3.5) |
| Diff-тред на строке, которой нет в текущем диффе, или с `head_sha`, отличным от `DiffRefs.HeadSHA` (устарел) | На вкладке Diff не показывается; в Discussions — как раньше, с `путь:строка` |
| Комментарий к строке после пуша в MR | GitLab отвечает 400 — тост с текстом сервера и «обнови (r)», текст формы сохранён |
| Задача To-Do без проекта (epic группы) | Project — `—`, `enter` открывает `target_url` в браузере |
| Цель To-Do удалена или нет доступа | `enter` → MR detail / issue получает 404 → тост «не найдено или нет доступа»; задачу можно отметить `x` |
| New MR из ветки, которой нет на сервере | Создание запрещено, «сначала git push» (3.18) |
| New MR, открытый MR из ветки уже есть | Confirm «Открыть его?» (3.18); если сервер всё же ответил 409 — тост с его текстом |
| New MR у проекта без шаблонов описания | Поле «Шаблон» показывает «без шаблона», запрос не повторяется |

## 13. Принятые допущения и открытые вопросы

### 13.1. Принятые допущения

1. **Bubble Tea v2** (и v2 всей экосистемы Charm). Обоснование — 6.2.
2. **GraphQL — свой тонкий клиент**, не genqlient. Обоснование — 5.1.
3. **Фильтр по проекту в workspace сливается с режимом проекта.** Обоснование — 2.7.
4. **Хоткеи:**
   - `m` — фильтр «я» везде, `M` — merge с выбором «сейчас / auto-merge» в диалоге;
   - checkout — `C`, язык — `ctrl+l`;
   - `L` в контексте MR — список ссылок MR (метки issue после MVP — `L` в Issues);
   - в Pipeline `h/l` — стейджи, лог — `enter`; в списке пайплайнов `l` — лог упавшей джобы.
5. **Списки MR и пайплайнов идут через GraphQL в обоих режимах.** REST-списки не отдают head pipeline, апрувы и длительность, которые нужны в колонках. Один фрагмент на оба режима. Остальное (детали пайплайна, лог, теги, issues, мутации) — REST.
6. **Теги — только REST** (в GraphQL нет списка тегов). Workspace Tags делает до 2 REST-запросов на проект, параллельно не больше 4.
7. **«Ждут меня»** в табе «Проекты» = открытые MR, где я ревьюер. Фильтр «я» в табах = автор ∪ assignee ∪ ревьюер, как в макете.
8. **Размер страницы режима проекта — 20** (бриф: «10+»): заполняет экран при той же цене запроса. Настраивается через `project.page_size`.
9. **Один инстанс за запуск.** Remote на другой хост — экран 2.4, а не переключение инстанса.
10. **SSH-алиасы** поддерживаются только через `host_aliases` в конфиге. `~/.ssh/config` и `url.insteadOf` не разбираем.
11. **Workspace из группы** ограничен 100 самыми активными проектами без архивных.
12. **Подтверждения:**
    - confirm-модалка: merge, cancel, delete tag, rebase, close issue, создание тега;
    - run pipeline и play job подтверждаются своей формой;
    - approve и checkout — без подтверждения (обратимы).
13. **Формы:**
    - переменные в Run pipeline редактируются как таблица (`a`/`d`/`enter`), а не через `ctrl+a`/`ctrl+d` из макета: конфликт с readline;
    - версия тега выбирается в Select, а не через `ctrl+n`/`ctrl+j`: `ctrl+j` — это Enter.
14. **Комментарий к MR** (общий, не к строке) делаем в M3 вместе с комментариями issue: тот же компонент. Комментарий к строке (T35) — тот же компонент с позицией.
15. **Минимальная версия GitLab** — 16.0. Auto-merge выбирает параметр по версии (5.5).
16. **Лог:** полный `GET /trace` каждые 3 с с разбором только хвоста. Обрезка в памяти — 50 000 строк.
17. **Диски:** на диск пишутся только конфиг, `state.json` (недавние, раскрытые группы и отмеченные в `P` проекты workspace) и кэш starred и метаданных workspace. Данные MR, пайплайнов и логов на диск не попадают.
18. **Макеты** задают раскладку и тексты, а не цвета. Цвета — по разделу 9.
19. **Fetch и pull:**
    - через системный git, pull только fast-forward (`merge --ff-only @{u}`);
    - fetch затрагивает и серые не-GitLab репозитории: это локальный git, к GitLab API он не относится;
    - процессы запускаются без терминала, авторизация — только неинтерактивная (agent, keychain, helpers);
    - хоткеи `u`/`U` не заняты ни в одном контексте. `f`/`p`, привычные по lazygit, у нас уже заняты фильтром и picker'ом (раздел 10.4).
20. **Дифф MR (T35):**
    - REST `/merge_requests/:iid/diffs`, а не GraphQL: в GraphQL у MR нет постраничного списка диффов с текстом ханков. `/changes` объявлен deprecated в 15.7;
    - unified diff одной прокруткой, без side-by-side: на 80 колонках два столбца кода не читаются;
    - без подсветки синтаксиса: цвета строк уже заняты ролями `+`/`-`, а Chroma дала бы свою палитру вместо 16 ANSI (раздел 9);
    - треды на строках — одной строкой со ссылкой на Discussions, а не карточкой внутри диффа: карточки уже есть, а дифф остаётся читаемым.
21. **To-Do (T36):** экран, а не таб: To-Do не принадлежат проекту или workspace. REST, как Issues: один запрос отдаёт цель, `target_url` и `X-Total`, а мутации у нас и так REST (п. 5). Счётчик в шапке — единственное фоновое обращение не от экрана на вершине (раз в 5 мин, один запрос с `per_page=1`).
22. **New MR (T37):** экран-форма на стеке, а не оверлей: полей больше десятка, а описанию нужна высота. Свои контролы, не huh, — как Run pipeline и New tag: подсказки с сервера, чипы, кнопка в фокусе. Создание MR из форка — позже (#56).
