# gitlab-tui

Терминальный клиент GitLab на Go + Bubble Tea v2 для личного использования. Два режима: проект (в папке с `.git`) и workspace (папка с проектами, батч-запросы GraphQL по всем сразу). Self-hosted GitLab — первоклассный сценарий.

- Спецификация: [docs/SPEC.md](docs/SPEC.md) — источник истины по поведению, хоткеям, API и архитектуре.
- Задачи и вехи: [GitHub Issues](https://github.com/4aykovski/glview/issues), дорожная карта — [#36](https://github.com/4aykovski/glview/issues/36) (M0 каркас → M1 режим проекта → M2 workspace и поиск → M3 теги, issues, полировка). Текстового списка задач в репозитории нет — см. «Задачи — GitHub Issues».
- Дизайн экранов: [docs/design/](docs/design/README.md) — локальная копия канваса https://claude.ai/artifact/XeDkUTkXVZ2Dg6sFAnmai2. Раскладка, разделители, рамки и тексты обязательны; hex-цвета и размеры шрифта иллюстративные (что именно — в README папки).

## Конфиденциальность — жёсткий запрет

Репозиторий публичный. В него, в историю git и в GitHub (коммиты, сообщения коммитов, ветки, PR, issues, комментарии) **НИЧЕГО конфиденциального попадать не должно — никогда, ни в каком виде**. Правило важнее любой задачи, удобства теста или просьбы «на минутку».

Запрещено всё, что пришло с рабочих систем или про них говорит:
- хосты и URL рабочих инстансов, внутренние домены и ссылки (вики, чаты, трекеры);
- названия групп, проектов, репозиториев, сервисов, команд, организаций;
- номера и ссылки MR, issues, пайплайнов, джоб, задач трекера (ключи вида `ABC-123`);
- имена, логины, e-mail коллег и свои рабочие учётные данные;
- токены, ключи, пароли, куки, конфиги с ними — даже «просроченные»;
- логи, трейсы, ответы API, отчёты ботов, скриншоты и снимки терминала с рабочих инстансов;
- куски рабочего кода и комментариев к нему.

Как работать:
- Фикстуры, golden-снимки, примеры в SPEC и OpenSpec — только выдуманные данные: `gitlab.example.com`, `platform/route-service`, `anna.k`, `egor`, `!479`. Нужна структура реального ответа — пересобери её руками на выдуманных данных, а не копируй.
- Результаты проверок на рабочем инстансе в репозиторий не пишутся; в документах — только «проверено на рабочем инстансе», без хостов, проектов, номеров и имён.
- Перед **каждым** коммитом из любой сессии (и в каждом субагенте): `make test lint confidential` зелёные, `git config --get core.hooksPath` = `scripts/githooks` (иначе `make hooks`), и глазами просмотреть `git diff --cached` и текст коммита на предмет перечисленного выше.
- Хуки `pre-commit`, `commit-msg`, `pre-push` (`scripts/githooks/confidential.sh`) проверяют добавленные строки, пути, сообщения и авторов по локальному списку `.confidential-patterns` (в `.gitignore`, в репозиторий не попадает) и по встроенным проверкам токенов, e-mail и внутренних хостов. Обходить их (`--no-verify`, `-n`, отключение `core.hooksPath`, правка хука ради прохода) **запрещено**. Ложное срабатывание — правь данные; новое конфиденциальное слово — добавь в `.confidential-patterns`.
- Задание субагенту обязано включать это правило.
- Если конфиденциальное уже попало в коммит — остановиться, не пушить, сообщить пользователю.

## Команды

```sh
make build   # бинарь в ./bin/gitlab-tui
make test    # go test ./...
make lint    # golangci-lint run
make run     # собрать и запустить
make hooks   # включить git-хуки проверки конфиденциальности (один раз после клона)
make confidential  # проверить все файлы репозитория теми же правилами
```

## Стек

Go 1.26, `charm.land/bubbletea/v2`, `charm.land/bubbles/v2`, `charm.land/lipgloss/v2`, `charm.land/huh/v2`, `charm.land/glamour/v2`, `gitlab.com/gitlab-org/api/client-go` (REST), свой тонкий GraphQL-клиент на net/http.

## Архитектура (кратко, подробно — SPEC §6)

```
cmd/gitlab-tui/         точка входа, флаги, сборка зависимостей
internal/config/        YAML-конфиг, XDG, цепочка хоста и токена
internal/glab/          опциональный glab: токен, exec-действия
internal/gitremote/     .git без вызова git: config, HEAD, remote URL, сканер
internal/gitexec/       системный git: fetch, pull --ff-only (M2)
internal/gitlab/        доменные типы и интерфейсы; rest/, graphql/, fake/
internal/cache/         TTL + stale-while-revalidate
internal/i18n/          Messages en/ru, плюрализация
internal/ui/app/        корневая модель, стек экранов, тосты
internal/ui/common/     Theme/Styles, keymap, footer, confirm, help
internal/ui/screens/    экраны
```

## Правила

- `internal/ui/...` не импортирует client-go, `gitlab/rest`, `gitlab/graphql` — только `internal/gitlab` (типы и интерфейсы). Проверяется depguard в `make lint`.
- Экраны не знают цветов: никаких `lipgloss.Color(...)` в `ui/screens` — только стили из `common.Styles`. Цвета — 16 ANSI через `Theme`.
- Все строки интерфейса — через `internal/i18n` (en и ru заполняются вместе, тест на полноту). Данные GitLab и статусы пайплайнов не переводятся.
- Каждый запрос — `tea.Cmd` с типизированным msg, несущим `Gen`; ответы со старым поколением выбрасываются. Поллинг — только у экрана на вершине стека.
- Деструктивные действия — через confirm-модалку.
- Токен никогда не пишется в логи и вывод; конфиг с токеном — права 0600.
- `.git` читаем файлами, `git` как процесс — только в `internal/gitexec`.
- Код, идентификаторы и комментарии — на английском; документация, OpenSpec-артефакты, коммит-сообщения — на русском.

## Процесс

- Планирование — OpenSpec (`openspec/`): одна change на веху, `/opsx:propose` → `/opsx:apply` → `/opsx:archive`.
- Ветка на веху: `m0`, `m1`, `m2`, `m3` от `main`. Коммиты небольшие, по issue задачи (`T03: gitremote ... (#3)`).
- Перед коммитом: `make test lint confidential` зелёные, хуки включены (см. «Конфиденциальность»).
- Решения, расходящиеся со SPEC, — сначала правка SPEC (и design.md change), потом код.

## Задачи — GitHub Issues

Источник истины по задачам — issues репозитория (через `gh`), а не файлы в репозитории. Дорожная карта — #36. Вехи GitHub: `M0 — каркас`, `M1 — режим проекта`, `M2 — workspace, GraphQL-батчинг, поиск`, `M3 — теги, issues, формы, полировка`, `После MVP`. Метки: `задача`, `ручная проверка`, `после MVP`.

- Перед работой — прочитать issue (`gh issue view <N>`): «Что», «Готово, когда», «Зависит от»; открытые зависимости — сначала они. Список задач вехи: `gh issue list --milestone "<веха>" --state all`.
- OpenSpec-change вехи строится по issues этой вехи; в proposal и tasks.md — ссылки `#N`.
- Задачи T01–T25 — issues #1–#25; у новых задач номер `Txx` и номер issue расходятся, в заголовке — `Txx: …`.
- Сообщение коммита ссылается на issue: `T11: … (#11)`. `Closes #N` не пишем — issue закрывается вручную.
- По ходу работы отмечать чекбоксы «Готово, когда» в issue (`gh issue edit <N> --body-file …`). Issue закрывается (`gh issue close <N> --reason completed --comment "<коммит>"`) после пуша, когда отмечены все пункты. Не сделанная ручная проверка на живом инстансе — issue остаётся открытым, пункт переносится в «Осталось».
- Новая работа, найденная проблема, отложенная идея — новый issue с вехой и меткой (отложенное — веха `После MVP`), ссылка на него — в дорожную карту #36.
- Issues, комментарии и PR публичны: правило «Конфиденциальность» действует целиком. Результаты проверки на рабочем инстансе — только «проверено», без хостов, проектов, номеров, имён, логов и скриншотов. Текст перед `gh issue create/edit/comment` — в файл и через `scripts/githooks/confidential.sh msg <file>`.
